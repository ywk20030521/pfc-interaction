# PFC Interaction 4.0 技术报告

**版本定位：** 4.0 目标架构与实施规划  
**建设范围：** PFC Interaction Skill 及其六个专业科研模块  
**实施策略：** 分两批建设，逐步形成完整科研协作闭环  
**核心原则：** Agent 主导科研协作，人机交互贯穿全过程，专业模块提供可验证的科研能力

---

## 一、项目定位与建设目标

### 1.1 项目定位

PFC Interaction 4.0 的目标不是简单扩充若干 PFC 操作指令，而是将现有交互能力发展为面向 PFC2D/PFC3D 数值模拟研究的智能科研协作 Skill。

它应当支持研究人员从提出科研问题开始，逐步完成研究规划、实验设计、数值建模、仿真执行、科学诊断、数据分析和研究结论整理。

其中，人与 Agent 的交互并非附属功能，而是科研工作流中发生频率最高、对科研正确性影响最大的过程之一。

科研人员需要持续参与以下决策：

- 明确研究目标、研究对象和研究边界；
- 确认实验条件、参数范围和对照组；
- 审核模型假设、接触模型和边界条件；
- 决定仿真运行方式、检查点和异常处理策略；
- 判断计算异常究竟属于数值问题还是物理问题；
- 确认数据处理口径、分析指标和结果解释；
- 决定是否修改模型、调整参数并重新计算。

因此，PFC Interaction 4.0 应当将人机交互能力建设为核心基础能力，并让六个专业模块通过统一的交互机制与用户协作。

### 1.2 建设目标

4.0 需要实现以下目标：

1. **科研任务可规划：** 将自然语言科研问题转化为有边界、有步骤、有交付物的研究任务。
2. **实验方案可设计：** 根据研究目标生成可执行的实验方案和参数矩阵。
3. **PFC 模型可构建：** 根据实验设计生成、修改和检查 PFC2D/PFC3D 模型。
4. **仿真过程可管理：** 支持运行、检查、暂停、恢复、异常处理和重复执行。
5. **科研问题可诊断：** 对模型、数值计算、物理行为和数据质量进行分层诊断。
6. **计算结果可分析：** 将原始计算数据转化为可解释、可比较、可复核的科研指标。
7. **人机协作可追溯：** 关键决策、用户确认、执行操作和结果证据之间形成明确关联。
8. **科研工作可迭代：** 根据诊断和分析结果调整实验设计、模型或参数，形成研究闭环。

### 1.3 设计原则

| 原则 | 技术要求 |
|---|---|
| Agent 主导 | Agent 是唯一的科研语义理解、分析和任务协调主体 |
| 人类保留决策权 | 关键科研假设、参数选择和高影响操作由用户确认 |
| Skill 专业化 | 每个专业模块具有明确职责、输入、输出和验收标准 |
| 工具职责分离 | PFC 执行与状态访问由现有 Itasca MCP/Bridge 工具链承担 |
| 证据驱动 | 结论必须区分实际执行证据、计算结果和推断 |
| 渐进式建设 | 先建立研究设计与建模基础，再扩展诊断和分析能力 |
| 不重复建设 | 复用已有交互、执行和可视化能力，不重复实现已有功能 |

## 二、总体架构

### 2.1 架构组成

PFC Interaction 4.0 由一个核心交互与协作层，以及六个专业科研模块组成。

```text
                  研究人员
                     │
          自然语言交互 / 结构化交互
                     │
        ┌────────────────────────┐
        │  PFC Interaction Core  │
        │                        │
        │  需求澄清               │
        │  人机协作与决策确认      │
        │  任务协调               │
        │  用户授权               │
        │  证据与状态管理          │
        │  工作流组织             │
        └────────────┬───────────┘
                     │
        ┌────────────┴────────────┐
        │      六个专业科研模块     │
        ├─────────────────────────┤
        │ M1 Research Planning    │
        │ M2 Experiment Design    │
        │ M3 PFC Modeling         │
        │ M4 Simulation Management│
        │ M5 Scientific Diagnosis │
        │ M6 Scientific Analysis  │
        └────────────┬────────────┘
                     │
        ┌────────────┴────────────┐
        │    PFC 工具执行能力       │
        │                          │
        │ Itasca MCP / Bridge      │
        │ PFC2D / PFC3D            │
        │ Python API / 数据文件     │
        └──────────────────────────┘
                     │
        ┌────────────┴────────────┐
        │     研究结果与科研资产    │
        │                          │
        │ 研究方案 / 实验矩阵       │
        │ PFC 模型 / 运行记录       │
        │ 诊断记录 / 分析数据       │
        │ 结论 / 报告 / 可视化结果  │
        └──────────────────────────┘
```

已有 Scientific Visualization 能力由现有 Visualization Skill 提供，作为结果展示和科研图表输出能力复用，不纳入本次六个专业模块的建设范围。

### 2.2 核心交互层与专业模块的关系

核心交互层不是简单的聊天界面，而是所有专业模块共同遵循的协作机制。

它负责：

- 接收和理解用户提出的科研需求；
- 判断当前科研任务处于哪个阶段；
- 识别尚未明确的条件和需要用户决策的问题；
- 将任务分配给适当的专业模块；
- 对关键参数、假设和操作进行确认；
- 将用户反馈传递给专业模块；
- 对执行过程、决策和证据进行关联；
- 在任务失败或条件变化时组织重新规划。

专业模块不得各自建立互相独立的人机交互体系。它们应当统一使用 PFC Interaction Core 提供的交互能力。

## 三、核心能力：人机交互与科研协作

### 3.1 为什么必须建设为核心能力

PFC 数值模拟不是完全确定性的自动化任务。

即使 Agent 能够生成脚本、调用 PFC 和分析数据，也不能自动替代研究人员对科研问题的判断。

例如：

- Agent 可以提出接触模型建议，但不能在缺乏依据时擅自确定材料本构假设；
- Agent 可以生成参数矩阵，但不能擅自改变研究人员设定的实验边界；
- Agent 可以识别计算异常，但不能把所有异常都自动归结为数值错误；
- Agent 可以计算应力—应变曲线，但不能在数据质量不合格时将其解释为有效物理规律。

因此，人机交互必须同时具备科研语义理解、决策确认和执行授权能力。

### 3.2 交互方式

采用双通道设计：

**通道一：Agent Native Chat**

主要用于：

- 科研问题讨论；
- 研究思路梳理；
- 实验方案讨论；
- 模型假设和物理机制分析；
- 结果解释；
- 研究决策。

这是默认交互通道。

**通道二：AUQ 结构化交互**

主要用于：

- 多参数选择；
- 实验条件确认；
- 检查点决策；
- 异常处理选择；
- 批量任务审批；
- 需要明确结构化答案的交互。

AUQ 是可选的辅助交互通道，不取代 Agent，也不直接获得 PFC 执行授权。

两种通道需要保持语义一致，避免同一个问题被重复询问。双通道运行时去重仍属于待完成的验证事项，不能仅凭设计存在就认定已经通过。

### 3.3 交互事件类型

| 交互类型 | 典型场景 | 处理要求 |
|---|---|---|
| 需求澄清 | 研究目标不明确 | 向用户询问必要条件 |
| 科研决策 | 接触模型、物理假设 | 提供依据并由用户确认 |
| 参数确认 | 实验参数和范围 | 展示参数及单位、默认值和影响 |
| 执行授权 | 运行、覆盖或重置模型 | 明确操作范围和影响 |
| 检查点决策 | 长时间计算阶段 | 提供当前状态和可选后续动作 |
| 异常处理 | 计算中断或数据异常 | 提供诊断证据和处理建议 |
| 结果确认 | 数据口径和分析结论 | 说明依据、限制和不确定性 |

### 3.4 交互状态管理

每次需要用户参与的任务，应当具有明确状态：

1. `PENDING`：等待用户决策；
2. `PRESENTED`：已向用户展示问题和选项；
3. `APPROVED`：用户已明确批准；
4. `REJECTED`：用户拒绝；
5. `EXPIRED`：决策条件已失效；
6. `EXECUTED`：批准的操作已执行；
7. `FAILED`：操作执行失败。

批准状态不能等同于执行成功。

例如，用户批准运行某个实验，只代表获得了执行授权；只有实际调用 PFC 工具并获得执行证据后，才能将其标记为执行成功。

### 3.5 交互与授权边界

必须明确区分以下三种行为：

- **讨论：** Agent 与用户讨论科研问题，不产生执行授权。
- **确认：** 用户确认实验方案或某个科研决策。
- **授权：** 用户明确允许执行具有实际影响的操作。

特别是 AUQ 返回的选项结果，不能自动视为执行授权。Agent 必须结合当前任务状态、授权范围和执行策略进行判断。

### 3.6 交互质量验收

核心交互层应通过以下验收：

- 用户可以通过自然语言完成完整科研讨论；
- 需要结构化回答时可以调用 AUQ；
- 用户拒绝后不得继续执行被拒绝的操作；
- 参数发生变化后，旧审批不得自动沿用；
- 重试时能够识别原任务和已完成步骤；
- 任务执行结果能够关联对应的用户决策；
- 失败、取消和超时状态能够正确反馈；
- 不得把“用户批准”描述为“PFC 已执行成功”。

## 四、六个专业科研模块

### M1：Research Planning——科研规划模块

<em>第一批建设</em>

#### 4.1.1 模块定位

将研究人员提出的自然语言科研问题，转化为结构化、可执行、可迭代的研究计划。

该模块解决的是“研究什么、为什么研究、需要回答哪些问题、如何证明结论”的问题。

#### 4.1.2 核心功能

1. 科研问题识别；
2. 研究目标与研究对象提取；
3. 研究范围与边界条件识别；
4. 科学假设整理；
5. 研究变量与响应指标识别；
6. 研究内容拆分；
7. 研究路线制定；
8. 研究任务与交付物定义；
9. 研究计划完整性检查。

#### 4.1.3 技术实现要求

输入可以是自然语言描述、已有研究方案、PFC 项目资料或实验数据说明。

模块首先提取：

- 研究对象；
- 研究目的；
- 主要科学问题；
- 研究假设；
- 自变量；
- 因变量；
- 控制变量；
- 约束条件；
- 预期研究成果。

对于信息不完整的研究问题，应通过 PFC Interaction Core 与用户进行多轮澄清。

不得为了让计划看起来完整而自行编造实验条件、材料参数或科学假设。

#### 4.1.4 标准输出

- `research_question.md`：研究问题；
- `research_plan.md`：研究计划；
- `research_hypotheses.md`：研究假设；
- `research_workflow.md`：研究路线；
- `research_requirements.json`：结构化研究要求。

#### 4.1.5 验收标准

- 能够将模糊问题整理为明确的研究目标；
- 能够识别缺失条件并提出必要问题；
- 能够区分用户提供的事实与 Agent 提出的建议；
- 研究目标、实验变量和预期结果之间具有逻辑一致性；
- 研究人员确认后才能进入实验设计阶段。

### M2：Experiment Design——实验设计模块

<em>第一批建设</em>

#### 4.2.1 模块定位

根据研究计划，将科研问题转化为可执行的 PFC 数值实验方案。

该模块解决的是“如何设计实验、改变哪些参数、设置哪些对照、需要计算哪些工况”的问题。

#### 4.2.2 核心功能

1. 实验类型识别；
2. 实验方案设计；
3. 变量与参数体系设计；
4. 参数范围和取值设计；
5. 单因素与多因素实验设计；
6. 对照组与基准组设计；
7. 实验工况矩阵生成；
8. 重复试验和敏感性分析设计；
9. 实验方案可执行性检查。

#### 4.2.3 技术实现要求

模块需要理解常见 PFC 实验类型，例如：

- 单轴压缩；
- 三轴压缩；
- 巴西劈裂；
- 直剪试验；
- 岩体结构面剪切；
- 颗粒流动；
- 边坡稳定性模拟；
- 颗粒破碎与裂纹演化。

实验设计必须结合具体研究问题，而不是仅根据实验名称套用固定模板。

例如，单轴压缩实验需要明确：

- 试样几何形状；
- 颗粒粒径及级配；
- 颗粒密度；
- 接触模型；
- 细观力学参数；
- 加载方式；
- 加载速率；
- 伺服控制方式；
- 应力和应变计算口径；
- 破坏判据；
- 输出指标。

对于多因素实验，需要生成完整参数矩阵，并明确每个工况的参数差异。

#### 4.2.4 标准输出

- `experiment_design.md`：实验设计说明；
- `parameter_schema.json`：参数定义；
- `experiment_matrix.csv`：实验工况矩阵；
- `control_groups.md`：对照组设计；
- `measurement_plan.md`：数据采集和测量计划。

#### 4.2.5 验收标准

- 实验变量与研究问题相匹配；
- 参数单位、范围和取值规则明确；
- 对照组和试验组之间的差异可解释；
- 参数矩阵不存在未经说明的遗漏或重复；
- 实验方案能够被 M3 模块转换为 PFC 建模要求；
- 重要实验假设和参数选择经过用户确认。

### M3：PFC Modeling——数值建模模块

<em>第一批建设</em>

#### 4.3.1 模块定位

根据实验设计生成、检查和维护 PFC2D/PFC3D 数值模型。

该模块解决的是“如何把实验方案正确地转换为 PFC 模型”的问题。

#### 4.3.2 核心功能

1. PFC2D/PFC3D 模型类型识别；
2. 模型结构设计；
3. 几何与颗粒生成；
4. 颗粒分布和级配设置；
5. 接触模型选择；
6. 细观参数配置；
7. 边界条件设置；
8. 加载与伺服机制构建；
9. FISH/Python/PFC 命令脚本生成；
10. 模型完整性检查；
11. 模型初始化与平衡检查；
12. 模型版本和修改记录。

#### 4.3.3 技术实现要求

M3 必须具备 PFC 专业知识，而不能只是将自然语言机械转换成命令。

例如，生成单轴压缩模型时，需要考虑：

- 颗粒生成区域；
- 颗粒重叠和初始平衡；
- 墙体或加载边界；
- 接触模型及其参数；
- 试样尺寸；
- 加载控制；
- 应力和应变测量方法；
- 计算停止条件。

模型检查需要区分：

**语法检查：**
- 命令是否有效；
- 变量和函数是否定义；
- 脚本是否存在明显语法错误。

**结构检查：**
- 颗粒数量是否合理；
- 墙体和边界是否完整；
- 接触模型是否正确配置；
- 加载装置是否符合实验设计。

**物理检查：**
- 模型参数是否有明确依据；
- 边界条件是否与研究假设一致；
- 初始状态是否满足实验要求；
- 是否存在明显不合理的物理设置。

模型能够运行不代表模型具有科学有效性。

#### 4.3.4 标准输出

- `model_design.md`：模型设计说明；
- `model.dat` 或对应 PFC 脚本；
- `model_parameters.json`：模型参数；
- `model_validation.md`：模型检查报告；
- `model_manifest.json`：模型文件清单与版本信息。

#### 4.3.5 验收标准

- 支持 PFC2D 和 PFC3D；
- 能够依据实验矩阵生成不同工况模型；
- 模型参数与实验设计保持一致；
- 脚本能够通过对应 PFC 环境的实际执行验证；
- 能够识别常见语法、结构和物理设置问题；
- 模型修改有明确记录；
- 不得将脚本生成成功等同于模型验证通过。

### M4：Simulation Management——仿真管理模块

<em>第二批建设</em>

#### 4.4.1 模块定位

负责组织和管理 PFC 仿真的执行过程。

该模块解决的是“如何运行、如何监控、如何处理异常、如何保证计算任务有序完成”的问题。

#### 4.4.2 核心功能

1. 仿真任务创建；
2. PFC2D/PFC3D 执行环境识别；
3. 仿真脚本执行；
4. 多工况任务组织；
5. 仿真进度管理；
6. 检查点管理；
7. 运行状态检查；
8. 异常检测与中断处理；
9. 任务恢复与重跑；
10. 运行记录和结果完整性检查。

#### 4.4.3 技术实现要求

M4 不负责重新实现 PFC 的底层执行能力，而是通过现有 Itasca MCP/Bridge 工具链组织仿真任务。

需要建立明确的任务状态：

- `CREATED`
- `READY`
- `RUNNING`
- `PAUSED`
- `COMPLETED`
- `FAILED`
- `CANCELLED`
- `RECOVERING`

任务状态必须来源于实际执行信息，不能仅依据 Agent 的主观判断。

对于长时间仿真，需要支持检查点机制：

- 定期检查运行状态；
- 识别是否达到预设停止条件；
- 在约定检查点向用户反馈；
- 需要决策时暂停等待；
- 用户批准后继续；
- 发生异常时保留必要证据。

#### 4.4.4 标准输出

- `simulation_config.json`：仿真配置；
- `simulation_log`：运行日志；
- `simulation_status.json`：任务状态；
- `checkpoint_manifest.json`：检查点记录；
- `execution_report.md`：执行报告；
- `simulation_artifacts/`：仿真产生的数据文件。

#### 4.4.5 验收标准

- 能够调用现有 PFC 工具链完成真实仿真；
- 能够正确识别运行、完成、失败和中断状态；
- 检查点能够触发正确的人机交互；
- 用户拒绝继续时能够停止对应任务；
- 失败后能够根据实际状态决定恢复或重新运行；
- 不得将重复执行造成的数据覆盖或任务重复误报为成功；
- 运行结果必须有实际 PFC 执行证据。

### M5：Scientific Diagnosis——科学诊断模块

<em>第二批建设</em>

#### 4.5.1 模块定位

对 PFC 模型、仿真过程、数值计算和物理结果进行分层诊断。

该模块解决的是“为什么出现这个结果、结果是否可信、问题出在哪里”的问题。

#### 4.5.2 核心功能

1. 模型设置诊断；
2. 初始状态诊断；
3. 数值稳定性诊断；
4. 计算收敛性诊断；
5. 物理行为诊断；
6. 数据质量诊断；
7. 实验结果合理性诊断；
8. 异常原因定位；
9. 修正建议生成；
10. 重新计算条件判断。

#### 4.5.3 诊断体系

诊断必须采用分层结构。

| 诊断层级 | 主要检查对象 | 典型问题 |
|---|---|---|
| 模型层 | 模型结构与参数 | 接触模型错误、边界设置不合理 |
| 数值层 | 计算过程 | 不稳定、异常振荡、计算发散 |
| 物理层 | 物理行为 | 破坏模式不合理、响应与假设不符 |
| 数据层 | 输出数据 | 缺失、重复、异常值、单位不一致 |
| 结果层 | 科研结论 | 证据不足、结论超出数据支持范围 |

#### 4.5.4 技术实现要求

诊断不能仅依赖单个阈值。

例如，计算过程中出现较大的不平衡力，并不一定意味着模型失败，需要结合计算阶段、边界条件、加载方式和其他状态指标进行判断。

诊断结果应包含：

- 问题描述；
- 发现依据；
- 涉及的数据或日志；
- 可能原因；
- 原因可信程度；
- 建议处理措施；
- 是否需要用户确认；
- 是否建议重新计算。

必须区分已确认原因、可能原因和待验证假设。

#### 4.5.5 标准输出

- `diagnosis_report.md`：诊断报告；
- `diagnostic_evidence.json`：诊断证据；
- `anomaly_records.json`：异常记录；
- `correction_proposals.md`：修正建议；
- `revalidation_plan.md`：重新验证计划。

#### 4.5.6 验收标准

- 能够区分模型、数值、物理、数据和结果问题；
- 诊断结论必须有可追溯依据；
- 不得将推测描述为确定事实；
- 能够提出与问题类型相匹配的修正建议；
- 涉及科研假设和模型实质性改变时必须由用户确认；
- 修正后能够组织重新计算和复核。

---

### M6：Scientific Analysis——科学分析模块

<em>第二批建设</em>

#### 4.6.1 模块定位

对 PFC 仿真产生的数据进行提取、整理、计算、统计和对比，形成可用于科研解释的定量结果。

该模块解决的是“从仿真数据中获得什么科研信息”的问题。

#### 4.6.2 核心功能

1. 数据文件识别；
2. 数据读取和整理；
3. 单位与数据口径检查；
4. 应力—应变计算；
5. 力学参数计算；
6. 裂纹和破坏特征统计；
7. 颗粒运动与位移分析；
8. 接触网络分析；
9. 多工况结果比较；
10. 参数敏感性分析；
11. 统计分析；
12. 结果质量检查；
13. 分析结果解释。

#### 4.6.3 技术实现要求

M6 必须区分原始数据、处理数据和分析结果。

建议采用以下处理流程：

```text
PFC 原始输出
     │
     ▼
数据读取与格式识别
     │
     ▼
数据完整性检查
     │
     ▼
单位与口径统一
     │
     ▼
指标计算与统计
     │
     ▼
多工况对比分析
     │
     ▼
结果质量检查
     │
     ▼
科研解释与报告
```

不同实验类型需要采用不同的指标计算方法。

例如，单轴压缩实验可能涉及：

- 轴向应力；
- 轴向应变；
- 峰值强度；
- 峰值应变；
- 弹性模量；
- 泊松比；
- 裂纹数量；
- 裂纹类型；
- 破坏模式。

但这些指标不能全部机械套用。需要根据实际模型结构、测量方式和研究目标确定计算口径。

#### 4.6.4 标准输出

- `raw_data_manifest.json`：原始数据清单；
- `processed_data/`：处理后的数据；
- `analysis_config.json`：分析参数与口径；
- `analysis_results.json`：分析指标；
- `comparison_report.md`：工况比较报告；
- `analysis_report.md`：科研分析报告。

#### 4.6.5 验收标准

- 能够读取支持范围内的 PFC 数据；
- 原始数据保持可追溯；
- 单位和计算口径明确；
- 关键指标有独立计算验证；
- 多工况比较使用一致的数据口径；
- 数据质量不足时明确阻止或限制结论；
- 结果解释与实际数据相符。

## 五、第一批与第二批建设规划

### 5.1 批次划分

<em>第一批：建立科研问题到可执行模型的能力</em>

| 模块 | 名称 | 建设重点 |
|---|---|---|
| M1 | Research Planning | 科研问题、研究目标和研究路线 |
| M2 | Experiment Design | 实验方案、参数体系和工况矩阵 |
| M3 | PFC Modeling | PFC2D/PFC3D 模型与脚本构建 |

第一批的目标是让研究人员能够通过 PFC Interaction 完成从科研问题到 PFC 模型的准备过程。

第一批完成后，系统应当能够：

1. 理解研究人员的科研问题；
2. 形成结构化研究计划；
3. 设计具体实验方案；
4. 生成参数矩阵；
5. 构建 PFC 数值模型；
6. 通过人机交互确认关键科研假设；
7. 通过实际 PFC 环境验证模型。

<em>第二批：建立仿真执行到科研结果的能力</em>

| 模块 | 名称 | 建设重点 |
|---|---|---|
| M4 | Simulation Management | 仿真执行、监控、检查点和恢复 |
| M5 | Scientific Diagnosis | 模型、数值、物理和数据诊断 |
| M6 | Scientific Analysis | 数据提取、指标计算和结果分析 |

第二批的目标是把第一批生成的模型转化为完整的仿真结果和科研分析成果。

第二批完成后，系统应当能够：

1. 执行实验工况；
2. 管理仿真任务；
3. 识别计算异常；
4. 组织异常诊断和用户决策；
5. 处理和分析仿真数据；
6. 对不同工况进行比较；
7. 形成具有证据支持的科研结论。

### 5.2 为什么这样划分

第一批解决科研任务的前端问题：研究什么、如何实验、如何建立模型。

第二批解决科研任务的后端问题：如何运行、如何判断、如何获得可信结果。

这样的划分具有三个优点：

- 第一批可以在现有 PFC 执行工具基础上独立形成有价值的能力；
- 第二批能够直接复用第一批形成的实验方案和模型；
- 诊断与分析建立在真实仿真结果之上，避免过早建设缺乏数据支撑的高级能力。

需要强调：现有 PFC Interaction 已具备一定的任务协调、人机审批和执行协作基础。因此，M4 并不是从零开始建设，而是在现有能力上形成完整、标准化的仿真管理专业模块。

### 5.3 模块依赖关系

```text
M1 Research Planning
          │
          ▼
M2 Experiment Design
          │
          ▼
M3 PFC Modeling
          │
          ▼
M4 Simulation Management
          │
          ▼
M5 Scientific Diagnosis
          │
          ▼
M6 Scientific Analysis
          │
          ▼
科研结果与研究结论
```

实际科研过程不是严格单向的线性流程。

例如：

- M5 发现模型设置问题，可以返回 M3；
- M6 发现数据质量问题，可以返回 M4；
- M6 发现研究指标不足，可以返回 M2；
- 研究结果与原始假设不符，可以返回 M1 重新审视研究问题。

因此，4.0 必须支持跨模块迭代，而不能仅仅实现六个互不关联的功能。

## 六、模块之间的统一技术规范

### 6.1 统一输入输出

六个模块必须遵循统一的输入输出约定。

每个模块至少需要明确：

| 字段 | 说明 |
|---|---|
| Module ID | 模块唯一标识 |
| Module Version | 模块版本 |
| Task ID | 所属科研任务 |
| Input | 输入内容和来源 |
| Preconditions | 执行前置条件 |
| Execution | 模块执行过程 |
| Output | 标准化输出 |
| Evidence | 证据与来源 |
| Status | 模块执行状态 |
| Decisions | 需要用户确认的事项 |
| Limitations | 已知限制 |

模块不能只返回一段自然语言总结，而应当同时提供可被后续模块使用的结构化结果。

### 6.2 统一任务状态

建议模块统一采用以下状态：

- `NOT_STARTED`
- `READY`
- `RUNNING`
- `WAITING_FOR_USER`
- `COMPLETED`
- `FAILED`
- `BLOCKED`
- `CANCELLED`

`COMPLETED` 仅表示模块任务按照定义完成，不代表其科学结论已经获得充分验证。

### 6.3 统一证据要求

每个模块都必须区分：

1. 用户提供的信息；
2. PFC 实际执行获得的信息；
3. 数据处理计算得到的信息；
4. Agent 基于证据作出的推断；
5. 尚待用户确认的假设。

例如，M3 生成了一个模型脚本，不代表该脚本已在 PFC 中成功运行；M4 成功运行了脚本，也不代表 M5 已经确认模型具有物理合理性。

### 6.4 统一文件与成果管理

模块间通过明确的文件、结构化数据和任务状态传递信息。

不要求所有模块采用相同的数据格式，但需要保证：

- 文件命名具有明确语义；
- 文件版本可识别；
- 输入输出来源可追溯；
- 单位和数据口径明确；
- 结果能够被后续模块读取；
- 关键文件有完整性检查；
- 不覆盖未经确认的原始数据。

## 七、与现有 PFC Interaction 能力的关系

### 7.1 现有能力继续保留

4.0 不应推翻现有 PFC Interaction 的基本架构。

以下能力应继续作为核心基础：

- Agent 与用户的自然语言协作；
- 任务状态管理；
- 人工审批与拒绝；
- 异步交互；
- 执行授权边界；
- PFC 工具调用；
- 证据记录；
- 失败处理和重试机制。

六个专业模块应在这些能力之上构建，而不是分别重复开发。

### 7.2 现有工具链的职责

| 组成部分 | 职责 |
|---|---|
| PFC Interaction Core | 科研交互、任务协调、决策与授权 |
| 六个专业模块 | 科研方法、专业任务和结果处理 |
| Itasca MCP/Bridge | PFC 工具访问与执行 |
| PFC2D/PFC3D | 数值计算和模型运行 |
| Visualization Skill | 科研可视化与图表输出 |

特别需要明确：

- PFC Interaction 不直接替代 Itasca MCP/Bridge；
- 专业模块不重复实现底层 PFC 命令执行；
- Visualization Skill 不在本次六模块建设中重新开发；
- AUQ 不替代 Agent 的科研判断，也不直接执行 PFC 操作。

### 7.3 当前验证边界

现有 0.1.0 的验证结果不能直接作为 4.0 六个模块全部完成的证据。

根据目前已知验证记录：

| 能力 | 当前情况 |
|---|---|
| PFC2D/PFC3D Console 基础验证 | T1–T8 已通过 |
| E2E 人机协作闭环 | 已有真实执行验证 |
| 检查点决策与异常修正重跑 | 已有实测 |
| AUQ npm CLI 异步交互 | A1–A5 已通过 |
| AUQ MCP 工具层异步交互 | 已通过相关工具层验证 |
| AUQ 宿主集成 | A8 尚未通过 |
| Native Chat/AUQ 双通道去重 | 仅设计通过，尚未实测 |
| GUI 动态交互 | G1–G6 尚未通过 |
| 完整物理 E2E | 有限场景验证，物理曲线独立标定未通过 |

因此，现阶段可以确认的是：PFC Interaction 已经具备一定的 PFC 工具协作和人机决策基础，但六个专业科研模块尚不能整体认定为 4.0 已实现能力。

## 八、实施路线与阶段验收

### 8.1 第一批实施顺序

建议按以下顺序实施：

**阶段 1：M1 Research Planning**

- 明确研究问题结构；
- 建立科研任务描述规范；
- 建立研究计划输出规范；
- 完成科研问题澄清测试。

**阶段 2：M2 Experiment Design**

- 建立实验类型知识与设计规范；
- 建立参数体系；
- 实现参数矩阵生成；
- 完成典型实验设计验证。

**阶段 3：M3 PFC Modeling**

- 建立 PFC2D/PFC3D 建模规范；
- 实现模型生成和脚本生成；
- 建立模型检查机制；
- 在真实 PFC 环境中执行验证。

第一批最终验收应至少完成一个端到端案例：

研究问题 → 研究计划 → 实验设计 → 参数矩阵 → PFC 模型 → PFC 实际运行验证。

### 8.2 第二批实施顺序

**阶段 4：M4 Simulation Management**

- 建立仿真任务状态规范；
- 实现检查点管理；
- 实现异常中断和恢复；
- 完成真实 PFC 仿真管理测试。

**阶段 5：M5 Scientific Diagnosis**

- 建立分层诊断体系；
- 建立异常类型和证据规范；
- 实现诊断建议；
- 完成典型异常场景验证。

**阶段 6：M6 Scientific Analysis**

- 建立数据读取和处理规范；
- 实现关键科研指标计算；
- 实现多工况对比；
- 完成分析结果独立复核。

第二批最终验收应至少完成：

PFC 模型 → 仿真执行 → 运行监控 → 异常诊断 → 数据处理 → 指标计算 → 多工况比较 → 科研分析报告。

### 8.3 总体验收标准

4.0 的验收不能只看模块是否能够调用，也不能只看脚本是否生成。

应当从五个层面进行验证：

| 验收层 | 主要内容 |
|---|---|
| 功能验收 | 模块功能是否完整 |
| 工程验收 | 输入输出、状态和异常处理是否正确 |
| 工具验收 | 是否能在真实 PFC 环境完成操作 |
| 科学验收 | 模型、数据和结论是否有科学依据 |
| 协作验收 | 用户决策、授权和执行证据是否形成闭环 |

最终必须通过完整科研案例验证模块之间的协作，而不是将六个模块的单项测试结果简单相加。

PFC Interaction 4.0 最终应当形成以下工作模式：

## 十、结论与建设边界

PFC Interaction 4.0 应定位为面向 PFC 数值模拟研究的智能科研协作 Skill。

其建设主体是六个专业科研模块：

**第一批：**

1. Research Planning；
2. Experiment Design；
3. PFC Modeling。

**第二批：**

4. Simulation Management；
5. Scientific Diagnosis；
6. Scientific Analysis。

人机交互、任务协调、用户授权、异步决策和证据管理作为 PFC Interaction Core 的核心能力，贯穿六个模块，不单独拆分为第七个业务模块。

已有 Scientific Visualization Skill 继续负责科研可视化能力，本次不重复建设。

4.0 的核心价值不在于让 Agent 能够执行更多 PFC 命令，而在于让 Agent 能够与研究人员协作，完成从科研问题到数值实验、从仿真计算到科学分析的完整过程。

**最终建设目标：让 PFC Interaction 从 PFC 操作交互能力，发展为具备科研规划、实验设计、数值建模、仿真管理、科学诊断和数据分析能力的完整科研协作 Skill。**

**版本状态声明：** 本报告描述的是 PFC Interaction 4.0 的目标架构、模块职责和实施方案，不代表六个模块已经全部实现或通过验收。各模块必须在完成开发和实际验证后，分别更新实现状态与验收结论。
