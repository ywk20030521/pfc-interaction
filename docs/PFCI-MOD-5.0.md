# PFC Interaction 5.0 — 科研专业模块与技术能力规范

**规范编号：** PFCI-MOD-5.0  
**规范级别：** 强制  
**适用对象：** M1–M6 专业模块、模块接口、科研方法知识和 PFC 技术实现  
**关联规范：** `01_总体架构与科研工作流规范.md`、`03_人机协作与决策协议规范.md`、`04_提问卡片强制设计规范_V2.md`

---

## 1. 目的

本规范冻结 M1–M6 的职责边界、输入输出、模块接口、协作规则和科研技术能力要求，重点消除模块功能重复。

模块是后台可调用的专业能力，不是六个独立 Agent，也不是六个必须按顺序出现的用户界面。Core 根据当前科研问题按需调用模块。

## 2. 模块职责总表

| 模块 | 唯一核心职责 | 不承担的职责 |
|---|---|---|
| M1 Research Planning | 定义研究问题、目标、假设和范围 | 具体工况矩阵、PFC 脚本、运行控制 |
| M2 Experiment Design | 将研究问题转为可比较的实验设计 | 模型脚本实现、仿真执行、最终数据计算 |
| M3 PFC Modeling | 将技术方案转为 PFC 模型 | 研究目标决策、运行调度、最终科学结论 |
| M4 Simulation Management | 管理仿真任务生命周期 | 科学原因诊断、科研指标解释 |
| M5 Scientific Diagnosis | 判断模型/数值/物理/数据问题及可信度 | 实际任务控制、全部统计分析 |
| M6 Scientific Analysis | 计算指标、比较工况、解释结果 | PFC 执行、全面异常诊断 |

## 3. M1 Research Planning — 科研规划

### 3.1 定位

回答“研究什么、为什么研究、需要回答哪些问题、研究边界是什么”。

### 3.2 必须具备的能力

- 从自然语言识别研究对象和研究背景；
- 梳理研究意义、研究目的和科学问题；
- 提出并管理研究假设；
- 明确研究范围、限制和预期成果；
- 识别概念层面的研究变量；
- 判断 PFC 数值模拟的适用性和潜在局限；
- 将用户已有资料纳入研究上下文；
- 指出目标不清、目标过多或研究问题不可验证之处。

### 3.3 输入与输出

输入：用户研究意图、文献/实验资料、既有模型、约束条件。

输出：
- `research_brief`
- `research_questions`
- `research_hypotheses`
- `research_scope`
- `research_requirements`

### 3.4 边界

M1 识别研究变量的科学含义；M2 决定如何将其操作化为实验变量。M1 可以提出研究路线，但不代替 M2 生成完整实验矩阵。

## 4. M2 Experiment Design — 实验设计

### 4.1 定位

将研究问题转化为有逻辑、可比较、可执行的实验设计。

### 4.2 必须具备的能力

- 识别适用实验类别；
- 讨论基准组、对照组和试验组；
- 定义自变量、因变量和控制变量；
- 识别变量混杂和归因风险；
- 设计单因素、多因素、正交、全因子或其他适用方案；
- 设计工况矩阵、重复试验和样本数量；
- 确定观测指标、输出频率和比较口径；
- 设计参数敏感性分析工况；
- 设计宏细观参数标定的试验矩阵。

### 4.3 对照组强制判断

每个适用研究任务都必须判断是否需要对照组/基准组。必须说明：
- 对照对象是什么；
- 对照用于排除或识别什么影响；
- 哪些条件保持一致；
- 哪些变量允许变化；
- 不设置对照时，如何保证比较或归因仍然成立。

### 4.4 输入与输出

输入：M1 研究问题、假设、约束和研究目标。

输出：
- `experiment_design`
- `variable_schema`
- `experiment_matrix`
- `control_group_spec`
- `measurement_plan`
- `calibration_design`

### 4.5 边界

M2 决定“试验哪些组合”；M3 决定“如何在 PFC 模型中实现这些条件”。M2 可提出参数范围，但不负责将其写入模型或宣称已标定。

## 5. M3 PFC Modeling — 数值建模

### 5.1 定位

将已确认的技术路线、实验条件和参数配置转化为可检查、可执行的 PFC2D/PFC3D 模型。

### 5.2 必须具备的能力

- 识别 PFC2D/PFC3D 适用性；
- 设计几何、试样和边界；
- 设计颗粒生成、粒径分布和级配；
- 选择并实现接触模型；
- 配置细观参数；
- 实现墙体、加载、伺服和停止条件；
- 实现 FISH/Python/PFC 命令脚本；
- 定义测量、历史记录和数据导出；
- 执行脚本静态检查和模型结构检查；
- 管理模型版本和变更记录。

### 5.3 模型检查分层

必须区分：
1. 脚本语法/命令检查；
2. 模型对象与结构检查；
3. 颗粒、接触和边界检查；
4. 初始平衡与数值状态检查；
5. 参数配置一致性检查；
6. 物理行为验证；
7. 真实 PFC 环境执行证据。

### 5.4 输入与输出

输入：技术路线、实验矩阵、模型要求、参数登记表和用户确认。

输出：
- 模型脚本；
- 模型配置；
- `model_manifest`；
- 测量与数据导出定义；
- 模型检查报告；
- 模型版本和变更记录。

### 5.5 边界

M3 可以配置候选参数并实现标定脚本，但不能独自宣布标定成功。标定结论必须由目标数据、误差计算、诊断和用户确认共同支撑。

## 6. M4 Simulation Management — 仿真管理

### 6.1 定位

管理仿真任务的执行生命周期，负责运行控制和任务证据，不负责科学解释。

### 6.2 必须具备的能力

- 检查执行环境和工具可用性；
- 核对模型、参数和任务版本；
- 创建并提交任务；
- 管理单工况和批量工况；
- 获取任务状态和日志；
- 管理检查点；
- 执行暂停、停止、中断、恢复和重跑；
- 检查输出文件完整性；
- 防止重复执行和未经授权覆盖；
- 将运行产物与任务、模型、参数版本关联。

### 6.3 输入与输出

输入：已确认的执行计划、模型、参数、执行授权和环境信息。

输出：
- `simulation_task`
- `simulation_status`
- `execution_log`
- `checkpoint_manifest`
- `simulation_artifacts`
- `execution_report`

### 6.4 边界

优先复用 Itasca MCP/Bridge 已提供的执行、状态、任务和中断能力。M4 是调用编排与生命周期管理，不得复制底层 PFC 执行器。

M4 可以按预设停止条件刹车，但不能把异常状态直接归因为接触模型错误、物理机制错误等科学原因。

## 7. M5 Scientific Diagnosis — 科学诊断

### 7.1 定位

基于模型、日志、状态和数据证据，判断模型、数值过程、物理行为和数据质量是否存在问题。

### 7.2 必须具备的能力

- 模型设置诊断；
- 初始状态和平衡诊断；
- 数值稳定性与收敛性诊断；
- 物理行为合理性诊断；
- 数据完整性和单位口径诊断；
- 异常原因假设与证据关联；
- 原因可信程度和不确定性表达；
- 修正建议、复核条件和重算建议。

### 7.3 诊断层级

| 层级 | 检查内容 | 例子 |
|---|---|---|
| 模型层 | 结构、参数、边界 | 接触模型或边界配置不适配 |
| 数值层 | 稳定性、收敛性 | 发散、振荡、异常步长 |
| 物理层 | 机制与响应 | 破坏模式不符合预期 |
| 数据层 | 完整性、单位、口径 | 缺失、重复、单位错配 |
| 解释层 | 结论与证据 | 结论超出数据支持范围 |

### 7.4 输入与输出

输入：模型清单、运行证据、日志、原始数据、研究假设和预期行为。

输出：
- `diagnosis_report`
- `anomaly_evidence`
- `cause_hypotheses`
- `confidence_and_limits`
- `recommended_actions`
- `revalidation_plan`

### 7.5 边界

M5 不直接控制任务生命周期；将暂停、恢复或重跑建议交由 Core/M4。M5 不替代 M6 完成全部统计和指标分析。诊断必须区分已确认原因、可能原因和待验证假设。

## 8. M6 Scientific Analysis — 科学分析

### 8.1 定位

将数据转化为可复核的科研指标、工况比较和有边界的科研解释。

### 8.2 必须具备的能力

- 读取原始输出和数据清单；
- 统一单位、坐标、时间步和口径；
- 计算力学指标；
- 分析应力—应变、位移、裂纹、颗粒运动和接触网络；
- 进行多工况比较；
- 进行适用的统计、敏感性和不确定性分析；
- 评估结果稳健性；
- 对照研究假设解释结果；
- 输出可供 Visualization Skill 使用的数据和图表需求。

### 8.3 输入与输出

输入：原始数据、数据字典、分析目标、指标定义、诊断信息和研究假设。

输出：
- `processed_data`
- `analysis_config`
- `analysis_results`
- `comparison_report`
- `analysis_report`
- `visualization_spec`
- `research_conclusion_draft`

### 8.4 边界

M6 可以指出结果与预期不一致，但不得仅凭不一致就判定数据错误。应结合 M5 诊断区分真实物理现象、模型局限、数值问题和数据处理问题。

Visualization Skill 负责图表和三维渲染实现；M6 负责提供数据、指标、单位和图表语义。

## 9. 跨模块重叠裁定

| 重叠主题 | 主责 | 协作 | 裁定 |
|---|---|---|---|
| 研究变量 vs 实验变量 | M1 / M2 | Core | M1 定义科学含义，M2 操作化 |
| 实验参数范围 vs 模型参数 | M2 / M3 | M6 | M2 设计范围，M3 配置实现 |
| 参数标定 | Core 组织 | M2–M6、用户 | 跨模块工作流，不归属单模块 |
| 模型检查 vs 科学诊断 | M3 / M5 | M4 | M3 前置结构检查，M5 独立诊断 |
| 异常检测 vs 异常处理 | M4 / M5 | Core、用户 | M4 控制，M5 诊断 |
| 数据质量 vs 数据分析 | M5 / M6 | Core | M5 可信度，M6 定量分析 |
| 结果解释 vs 研究问题 | M6 / M1 | 用户 | M6 解释结果，M1 更新研究问题 |
| 图表 vs 分析数据 | Visualization Skill / M6 | Core | 可视化实现与数据语义分离 |

## 10. 统一模块接口

每个模块必须声明以下接口字段：

```yaml
module_result:
  module_id: M1
  module_version: ""
  research_task_id: ""
  stage_id: ""
  input_refs: []
  preconditions: []
  status: completed
  outputs: []
  evidence: []
  decisions_required: []
  unresolved_items: []
  limitations: []
  affected_assets: []
  next_recommendation: ""
```

要求：
- 输入必须说明来源和版本；
- 输出必须可被其他模块读取；
- 关键结论必须关联证据；
- 未解决事项不得隐藏在普通文本中；
- 失败必须返回失败原因，不得伪装为完成；
- 模块不得自行修改其他模块拥有的状态。

## 11. 参数标定专项跨模块协议

标准闭环：

1. M2 定义标定实验、目标指标和工况矩阵；
2. Core 与用户确认目标、指标和接受标准；
3. M3 将参数写入模型并生成模型版本；
4. M4 执行标定工况并保存日志、输出；
5. M5 检查运行与数据可信度；
6. M6 计算模拟与目标之间的误差、敏感性和比较结果；
7. Core 主持参数调整讨论；
8. 用户确认下一轮参数方案；
9. M3 更新参数和模型版本；
10. 重复执行，直至达到预设标准或确认无法达到；
11. 保存最终参数、标定历史、误差和适用范围。

禁止：
- 只凭曲线“看起来接近”宣称标定成功；
- 没有目标数据和指标就自动调参；
- 不记录参数变更历史；
- 将单一拟合结果宣称为参数唯一解；
- 将未经验证的参数标记为已标定。

## 12. 专业能力验收

每个模块必须有：
- 正常案例；
- 边界案例；
- 输入不完整案例；
- 与相邻模块的接口案例；
- 失败和恢复案例；
- 证据可追溯案例。

端到端验收至少覆盖一个真实 PFC2D 或 PFC3D 科研任务。模块单测通过不代表科研闭环通过。
