# PFC Interaction 5.0 技术报告
## 讨论深度强化修订版（5.0.1）

**版本定位：** 面向复杂 PFC 数值模拟课题的持续科研协作 Skill  
**修订重点：** 深度科研讨论、迭代论证、课题连续性和科研档案  
**建设范围：** PFC Interaction Core + 六个专业模块 + 双通道人机协作 + 现有工具链适配  
**产品原则：** 轻量、可安装、Agent Native、科研问题驱动、证据可追溯  
**状态声明：** 本报告定义目标架构和验收要求，不代表全部能力已经实现。

---

## 一、为什么需要修订 5.0

### 1.1 之前 5.0 的不足

此前 5.0 已将工作流从“六模块顺序调用”调整为“六阶段科研流程 + 六个按需专业模块”，并提出持续讨论、统一上下文、决策状态和阶段回退。但这些内容仍偏向架构概念，缺少真正支撑复杂实验室研究的讨论机制。

主要不足：

1. **讨论深度没有操作化。** 只写“持续讨论”，没有定义一个科研议题需要经历哪些论证步骤。
2. **迭代机制不充分。** 没有区分初步澄清、方案论证、反方审查、修订综合和验证规划。
3. **轮数没有质量约束。** 系统可能用几个简单问题就宣称研究目标或实验设计已明确。
4. **研究人员隐性知识利用不足。** 没有系统获取实验经验、设备限制、失败经验和团队既有约定。
5. **跨会话连续性不够。** 没有把议题树、假设、分歧、决策理由、证据和方案版本作为长期课题资产。
6. **阶段推进容易过早收敛。** 缺少复杂议题最低讨论深度和阶段审查条件。
7. **Agent 的专业贡献不够明确。** 容易表现为连续追问，而不是提出分析、反例、竞争性解释和方案修订。

因此，本次不是增加几条提问规则，而是将核心工作对象从“问题”提升为“科研议题”，将交互机制从“问答循环”升级为“多轮科研论证循环”。

### 1.2 修订后的核心定位

**PFC Interaction 是能够围绕一个科研课题进行长期、多轮、深入讨论，并持续组织研究规划、实验设计、PFC 建模、参数标定、仿真执行、异常诊断和结果解释的轻量化科研协作 Skill。**

它不是只会按模板提问的问卷工具，不是只会生成研究计划的文本助手，不是只会生成 PFC 脚本的代码助手，不是只会调用 Itasca MCP 的工具代理，也不是必须依赖独立 Web 平台的重型系统。

### 1.3 核心成功标准

用户应当能够从一个不成熟的研究想法开始，与 Agent 反复讨论；Agent 能提出专业分析和质疑，用户能多次纠正和补充；系统能保存讨论演进，形成阶段性方案；后续实验和数据又能反向修正早期判断。最终得到的不只是文档，而是一套可追溯的科研过程和可验证的研究成果。

## 二、5.0.1 的核心设计变化

| 维度 | 原 5.0 侧重 | 5.0.1 强化 |
|---|---|---|
| 交互对象 | 问题与回答 | 科研议题及其演进 |
| 讨论过程 | 持续讨论循环 | 多阶段论证、质疑、修订和验证 |
| 轮数 | 不设固定问题数 | 按复杂度定义最低实质迭代深度 |
| Agent 角色 | 分析与建议 | 讨论主持者、共同分析者、反方审查者 |
| 用户知识 | 用户输入 | 系统性获取实验室隐性知识 |
| 上下文 | 当前研究上下文 | 课题级科研档案和版本历史 |
| 决策 | 确认/否决/暂缓 | 讨论成熟度、暂定决策、证据验证和失效 |
| 阶段推进 | 阶段完成条件 | 议题覆盖、论证完整、风险和未决项审查 |
| 卡片 | 结构化提问 | 深度讨论后的收敛和授权界面 |
| 验收 | 流程和模块验收 | 复杂课题、多轮论证、反方审查和证据驱动迭代 |

### 3.1 Core 内部能力

- **Research Context Manager：** 维护课题背景、用户事实、实验室约束、研究目标和当前状态。
- **Issue Tree & Backlog Manager：** 维护议题树、子议题、依赖、优先级、待讨论队列和重开事项。
- **Deep Discussion Engine：** 组织探索、澄清、方案论证、反方审查、参数协商、结果解释和阶段复盘。
- **Evidence & Hypothesis Manager：** 管理文献、实验资料、PFC 工具输出、计算结果、用户经验、Agent 推断和未验证假设。
- **Decision & Authorization Manager：** 管理方案决定、暂定结论、拒绝、暂缓、授权范围和决策失效。
- **Workflow Orchestrator：** 根据议题状态和阶段前置条件调用 M1–M6，允许并行、回退和重开。
- **Change & Review Manager：** 识别新证据或用户变更对既有决策、模型、参数、工况和结果的影响。
- **Research Archive Manager：** 维护课题级文件和摘要，避免长对话上下文丢失。

讨论引擎、议题管理和科研档案属于 Core 横向能力，不是第七个专业模块。

## 四、科研议题驱动的工作机制

### 4.1 从单个问题到议题树

一个真实研究课题不是一个问题，而是多个互相依赖的议题。例如“研究颗粒材料在不同加载条件下的破坏机制”可能拆为：

```text
课题：不同加载条件下颗粒材料破坏机制
├─ A. 科学问题
│  ├─ A1. 研究的破坏机制是什么？
│  ├─ A2. 现有理论解释的不足在哪里？
│  └─ A3. 哪些观测量能区分不同机制？
├─ B. 实验设计
│  ├─ B1. 加载条件如何分类？
│  ├─ B2. 是否设置基准组？
│  ├─ B3. 哪些变量必须控制？
│  └─ B4. 是否需要重复工况？
├─ C. PFC 模型
│  ├─ C1. 2D 或 3D？
│  ├─ C2. 接触模型如何选择？
│  ├─ C3. 颗粒级配和尺寸如何确定？
│  └─ C4. 如何验证模型？
├─ D. 参数
│  ├─ D1. 参数来源与范围？
│  ├─ D2. 参数耦合和可辨识性？
│  └─ D3. 标定指标与独立验证？
└─ E. 结果解释
   ├─ E1. 结果是否支持假设？
   ├─ E2. 是否存在其他解释？
   └─ E3. 结论的适用边界？
```

Agent 应逐步建立议题树，不得一次性把全部子问题倾倒给用户。优先处理对研究有效性影响最大的 P0/P1 议题。

### 4.2 议题生命周期

`OPEN → UNDER_DISCUSSION → NEEDS_EVIDENCE / NEEDS_USER_INPUT → PROVISIONAL / DECIDED → VALIDATED`

可从任何中间状态转为 `REOPENED`。被新决策替代的旧议题记录为 `SUPERSEDED`；证据推翻旧结论时记录为 `INVALIDATED`。

## 五、深度科研讨论引擎

### 5.1 议题循环

```text
确定议题
  ↓
复原研究背景和已知事实
  ↓
拆分子问题与依赖
  ↓
Agent 提出初步分析和候选方案
  ↓
用户补充专业经验、约束和判断
  ↓
Agent 进行反方审查、寻找反例和替代解释
  ↓
比较方案的科学性、可行性、成本和风险
  ↓
根据反馈修订方案
  ↓
形成阶段性综合、未决项和验证计划
  ↓
归档；继续讨论 / 暂定推进 / 正式决策
```

### 5.2 讨论深度等级

| 等级 | 类型 | 最低讨论过程 |
|---|---|---|
| D0 | 事实确认、简单信息 | 核对来源与语义 |
| D1 | 局部低风险选择 | 初步分析、用户反馈、修订/确认 |
| D2 | 多变量/多约束设计 | 初步方案、替代方案比较、质疑、用户反馈、修订综合 |
| D3 | 核心科学问题/假设/模型/标定/结论 | 多轮正反论证、竞争性解释、用户专业输入、修订、验证计划；有证据后才可标记验证 |

D2/D3 不得在首轮讨论后直接定案。最低迭代结构见规范 03。迭代次数不能机械计数，只有新增证据、分析、反例、方案变化或综合才算实质迭代。

### 5.3 Agent 的实质贡献

Agent 每轮必须至少完成一项：新的专业分析；对用户方案的逻辑审查；竞争性解释或反例；方案比较；新证据需求识别；参数/变量关系分析；方案修订；多轮讨论的高质量综合。

如果只是在问“还有吗”“是否确认”，则不构成有效科研讨论。

### 5.4 讨论模式

探索、澄清、方案论证、反方审查、参数协商、异常会诊、结果解释、阶段复盘。模式由 Core 根据议题选择，不需要用户理解内部模块。

## 六、六阶段科研工作流

### S1 研究对象与科学问题
明确研究对象、背景、意义、科学问题、假设、竞争性解释、研究边界和 PFC 适用性。不能只把用户一句话改写成研究计划。

### S2 实验类别与实验设计
讨论实验类别、对照组、变量、工况矩阵、重复性、测量指标、因果识别和计算成本。每项实验设计必须回扣科学问题。

### S3 技术方案与建模路线
讨论 PFC2D/PFC3D、颗粒生成、接触模型、边界加载、测量、数据输出、数值稳定性和模型验证。每项关键建模选择需说明替代方案和局限。

### S4 参数确定与标定
讨论参数来源、单位、初始值、范围、参数耦合、可辨识性、误差函数、标定工况、敏感性和独立验证。标定是跨模块闭环。

### S5 仿真执行与异常干预
管理真实运行、检查点、状态、日志、异常、暂停/恢复/重跑。M4 管运行，M5 诊断原因，Core 组织用户讨论。

### S6 结果分析与科研总结
分析数据、比较工况、检验假设、识别替代解释、评价不确定性、限定结论适用范围。必要时返回前序阶段。

六阶段是研究地图，不是严格单向流程。任何新证据都可以触发前序议题重开。

## 七、六个专业模块及边界

- **M1 Research Planning：** 研究对象、科学问题、假设、研究范围。
- **M2 Experiment Design：** 实验类别、对照、变量、工况矩阵、观测指标。
- **M3 PFC Modeling：** PFC 模型、接触模型、参数配置、边界、脚本和模型检查。
- **M4 Simulation Management：** 任务执行生命周期、检查点、暂停、恢复和重跑。
- **M5 Scientific Diagnosis：** 模型、数值、物理、数据和结果可信度诊断。
- **M6 Scientific Analysis：** 指标计算、统计、工况比较、假设检验和结果解释。

跨模块职责裁定和统一接口以规范 02 为准。参数标定由 Core 组织 M2–M6 协作，不归为单模块任务。

## 八、实验室知识与长期科研档案

必须保留用户研究背景和经验、课题目标与边界、议题树、已讨论方案及被否决原因、假设和争议、决策及理由、参数来源和版本、实验矩阵和模型版本、运行异常和诊断证据、结果解释和适用范围、待讨论事项。

推荐档案：
`PROJECT_CHARTER.md`、`ISSUE_TREE.md`、`DISCUSSION_LOG.md`、`HYPOTHESIS_REGISTER.md`、`DECISION_REGISTER.md`、`ASSUMPTION_REGISTER.md`、`EVIDENCE_INDEX.md`、`EXPERIMENT_DESIGN.md`、`EXPERIMENT_MATRIX.csv`、`PARAMETER_REGISTER.csv`、`MODEL_REGISTER.md`、`SIMULATION_LOG.md`、`ANOMALY_REGISTER.md`、`ANALYSIS_REGISTER.md`、`CHANGELOG.md`。

第一版不要求数据库。优先 Markdown/JSON/CSV 和 Agent 可访问的项目目录。若跨会话、跨 Agent 或多人协作成为硬需求，再评估持久化服务。

防止上下文膨胀：每轮只加载当前议题摘要、相关决策、证据引用、待讨论队列和变更影响摘要；原始讨论保留在档案中。

## 九、Native Chat 与 AUQ

Native Chat 是复杂科研讨论主通道。AUQ 是可选的结构化异步输入通道，适合明确参数、选项和审批。先讨论后卡片；同一事项只能有一个有效交互实例；AUQ 回答必须返回原议题上下文；AUQ 不直接调用 PFC 工具。AUQ 可选集成和宿主限制沿用既有人机协作架构决策。

## 十、决策、授权与证据

必须区分讨论、方案确认、执行授权、实际执行和科学验证。

事实分类：用户事实、用户经验、来源事实、工具观察、计算结果、Agent 推断、Agent 建议、未验证假设。

决策状态：提出、讨论中、暂定、确认、否决、暂缓、被替代、失效。科研成熟度：想法、问题成形、已论证、已审查、待验证、数据支持、限定范围内验证、未解决。

用户确认不等于科学验证；PFC 执行成功不等于物理模型正确。

## 十一、异常刹车与异常会诊

M4 监测任务状态并执行预设暂停/停止；M5 根据证据诊断原因；Core 组织用户讨论和决策；M3 修改模型/参数；M4 恢复或重跑；M6 对新结果比较和复核。

异常等级 L0 信息、L1 警告、L2 需要判断、L3 严重停止。阈值必须按实验类型定义。不得将异常检测阈值直接等同于科学原因。

## 十二、产品与工具边界

第一交付仍是轻量 Skill。复用 Agent 宿主 Native Chat、可选 AUQ、Itasca MCP/Bridge、PFC2D/PFC3D、Python API 和现有 Visualization Skill。Interaction 不复制 PFC 执行、任务状态和可视化渲染能力。独立 MCP、Web、数据库均为条件性扩展，不是 5.0.1 前置条件。

## 十三、实施优先级

### P0：科研连续性底座
统一课题上下文和档案；议题树、待讨论队列和议题状态；深度讨论协议；决策/证据/假设登记；跨会话恢复；取消固定问题数推进。

### P1：M1–M3 科研规划、实验设计与建模
复杂议题讨论；研究问题和实验设计论证；模型路线比较；模型假设与验证计划。

### P1 专项：参数确定与标定
参数来源；参数耦合和可辨识性；标定工况；误差/敏感性/独立验证；跨模块协作闭环。

### P2：M4–M5 执行管理与异常会诊
检查点；异常刹车；证据化诊断；恢复/重跑和变更影响。

### P2：M6 结果分析与科研总结
假设检验；竞争性解释；适用范围；Visualization Skill 数据接口。

## 十四、验收体系

### 14.1 对话深度验收
采用复杂科研课题，检查是否能从模糊想法建立问题树、开展 D2/D3 多轮论证、由 Agent 提出分析/反例/替代方案、吸收用户纠正、形成方案修订记录、不因回答几道问题自动结束，并保留未决事项和验证计划。

### 14.2 研究连续性验收
跨会话恢复议题和决策；不重复询问已有事实；记录被否决方案及理由；新证据触发旧议题重开；变更影响分析正确；上下文压缩不丢失关键约束。

### 14.3 专业科研验收
对照和变量逻辑成立；PFC 建模选择有依据；参数来源与标定过程可追溯；真实 PFC 执行证据存在；异常诊断区分事实和推断；分析结论不超出数据支持范围。

### 14.4 端到端案例
至少选择一个真实 PFC2D 或 PFC3D 复杂课题，贯通研究规划、实验设计、建模、参数标定、执行、异常诊断和结果分析；过程中至少出现一次用户修正、一次方案变更和一次基于新证据的议题重开。

### 14.5 量化指标
跟踪关键议题覆盖率、D2/D3 论证完整率、方案修订正确率、重复提问率、未决事项遗漏率、决策可追溯率、跨会话恢复成功率、变更影响识别率和用户对讨论实质推进的评价。不得把轮数本身作为唯一目标。

## 十五、最终结论

PFC Interaction 5.0.1 的核心不是让 Agent 问更多问题，而是让 Agent 真正参与科研思考：理解课题、拆解议题、提出分析、比较方案、挑战假设、吸收用户经验、修订设计、保留争议、组织验证，并根据新的实验数据持续更新研究认识。

**衡量系统是否达到目标，不看它问了多少题，而看它是否让研究人员与 Agent 共同把一个复杂课题一步步研究得更清楚、更严谨、更可验证。**
