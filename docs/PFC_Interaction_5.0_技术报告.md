# PFC Interaction 5.0 技术报告

**版本定位：** 面向 PFC2D/PFC3D 数值模拟研究的持续科研协作系统\
**文档性质：** 5.0 目标架构、工作流、模块职责、交互机制与实施验收规范\
**继承基础：** PFC Interaction 4.0 技术报告及既有 PFC Interaction
Core、AUQ、Itasca MCP/Bridge 能力\
**核心调整：** 从"六个专业模块串联"升级为"科研工作流驱动 + Core
持续主持讨论 + 专业能力按需协作"\
**实施原则：** 轻量、可复用、Agent
主导、人类保留科研决策权、证据驱动、渐进式实现

------------------------------------------------------------------------

## 文档说明

本报告以 PFC Interaction 4.0 技术报告为基础，保留其面向 PFC2D/PFC3D
科研协作的总体目标、六项专业能力、Agent Native Chat 与 AUQ
双通道、Itasca MCP/Bridge
工具职责分离、证据与授权边界，以及分阶段建设思路。

5.0 对 4.0 进行结构性调整，重点解决以下问题：

1.  六个专业模块之间存在职责交叉，尤其是研究变量与实验设计、参数设计与参数配置、异常检测与科学诊断、数据质量判断与结果分析。
2.  4.0
    将专业模块描述得较完整，但没有充分定义研究人员实际经历的连续科研工作流程。
3.  参数确定、参数标定、参数敏感性分析和参数修正缺少完整的跨模块闭环。
4.  人机交互主要定义了提问、确认、授权和状态记录，没有充分定义持续科研讨论、主动提出建议、方案比较、追问和阶段推进机制。
5.  结构化提问容易退化为有限问题收集，不能替代 Agent
    与研究人员之间的开放式科研讨论。
6.  需要明确区分用户可见的科研阶段、后台专业能力、Core 协调机制和底层
    PFC 执行工具，避免把它们混为同一层级。

本报告描述 5.0
的目标设计，不代表相关能力已经实现或通过验收。所有能力必须通过真实 PFC
环境和完整科研案例分别验证。

# 一、项目定位与 5.0 建设目标

## 1.1 项目定位

PFC Interaction 5.0 是面向 PFC2D/PFC3D 数值模拟研究的智能科研协作
Skill。

它不是简单的 PFC
命令生成器，也不是由若干固定问答表单组成的参数收集工具。它应当围绕研究人员提出的科研问题，持续组织研究讨论、实验设计、技术方案制定、参数确定与标定、仿真执行、异常干预、数据分析和科研总结。

系统的核心工作模式是：

-   研究人员提出科研问题、提供专业知识并参与关键判断；
-   Agent 理解研究意图，主持持续讨论，提出分析、建议、反例和风险；
-   Core 维护跨阶段科研上下文、讨论进度、决策状态和工作流；
-   专业模块按当前问题提供科研方法和技术能力；
-   Itasca MCP/Bridge 负责连接 PFC 工具环境，PFC2D/PFC3D 执行数值计算；
-   结果分析和诊断为前序研究阶段提供反馈，形成可迭代的科研闭环。

**5.0 的核心不是让 Agent 提出更多问题，而是让 Agent
能够围绕科研目标，与研究人员持续讨论并推动研究任务取得有依据的进展。**

## 1.2 建设目标

5.0 应具备以下能力：

1.  **研究问题可理解：**
    从自然语言、已有模型、实验资料和研究数据中识别研究对象、研究目的、科学问题及边界。
2.  **科研讨论可持续：**
    能够围绕一个问题进行多轮、有上下文、有推理、有反馈的讨论，不以固定问题数量作为结束条件。
3.  **实验方案可协商：**
    能够提出不同实验设计，比较其科学意义、适用条件、成本和局限，并根据用户意见修订。
4.  **技术路线可论证：** 能够讨论 PFC
    维度、接触模型、边界条件、加载方式、监测指标和验证策略，并明确依据与不确定性。
5.  **参数确定可迭代：**
    支持参数来源识别、初始取值、宏细观参数标定、敏感性分析、误差评价和参数修正。
6.  **模型构建可验证：** 根据已确认的实验和技术方案生成 PFC2D/PFC3D
    模型，并区分脚本生成、语法检查、实际运行和科学有效性验证。
7.  **仿真执行可管理：**
    支持任务执行、状态检查、检查点、暂停、中断、恢复和重跑。
8.  **异常干预可解释：**
    能够发现异常、提供证据、分析可能原因、提出修正方案，并在需要时请求用户决策。
9.  **结果分析可复核：**
    能够读取数据、统一单位与口径、计算指标、比较工况并说明结果限制。
10. **科研过程可追溯：**
    研究讨论、关键决策、参数版本、模型版本、执行记录、诊断结果和分析结论能够关联。
11. **研究过程可迭代：**
    允许从结果分析返回研究目标、实验设计、技术方案或参数标定阶段，而不是强制单向执行。

## 1.3 设计原则

  --------------------------------------------------------------------------------------------------------
  原则                                5.0 要求
  ----------------------------------- --------------------------------------------------------------------
  Agent 主导                          Agent 负责科研语义理解、讨论主持、专业推理和工作流推进

  人类保留决策权                      研究假设、关键实验设计、重大参数变更和高影响操作由用户决定

  讨论优先于表单                      开放式科研问题先通过 Native Chat
                                      讨论，结构化交互仅用于明确的选择、确认和审批

  阶段与模块分离                      六个科研阶段是用户可见工作流程，专业模块是后台能力，不要求一一对应

  专业能力协作                        一个科研问题可以调用多个模块，不要求模块独立完成整个阶段

  不重复建设                          复用已有 Core、AUQ、Itasca MCP/Bridge 和 Visualization Skill

  证据驱动                            区分用户事实、工具执行事实、数据计算结果、Agent 推断和待验证假设

  渐进式建设                          先实现可持续讨论和前端科研设计，再形成执行、诊断与分析闭环

  轻量实用                            不以建设大型全栈平台为目标，优先通过 Skill、现有 Agent Harness
                                      和工具链完成能力组织

  可追溯、可恢复                      决策、任务、模型和数据版本之间保持明确关联
  --------------------------------------------------------------------------------------------------------

# 二、5.0 总体架构

## 2.1 架构分层

5.0
采用四层架构，避免将交互机制、科研工作流、专业模块和底层工具混为一谈。

``` text
研究人员
   │
   ▼
用户交互层
   ├── Agent Native Chat：持续科研讨论（默认）
   └── AUQ：结构化提问、确认与异步决策（辅助）
   │
   ▼
PFC Interaction Core
   ├── Context Manager：科研上下文管理
   ├── Discussion Manager：持续讨论管理
   ├── Reasoning & Proposal：分析、方案与风险建议
   ├── Decision Manager：决策状态与审批管理
   └── Workflow Orchestrator：阶段推进与模块协调
   │
   ▼
科研工作流层（用户可见的六个阶段）
   ├── 1. 研究对象与科研目标
   ├── 2. 实验类别与实验设计
   ├── 3. 技术方案与建模路线
   ├── 4. 参数确定与标定
   ├── 5. 仿真执行与异常干预
   └── 6. 结果分析与科研总结
   │
   ▼
专业能力层（后台按需调用）
   ├── M1 Research Planning
   ├── M2 Experiment Design
   ├── M3 PFC Modeling
   ├── M4 Simulation Management
   ├── M5 Scientific Diagnosis
   └── M6 Scientific Analysis
   │
   ▼
工具与执行层
   ├── Itasca MCP / Bridge
   ├── PFC2D / PFC3D
   ├── Python API / 数据文件
   └── 现有 Scientific Visualization Skill
   │
   ▼
科研资产
   ├── 研究计划与讨论决策
   ├── 实验设计与参数矩阵
   ├── 模型脚本、参数和版本
   ├── 仿真任务、日志和检查点
   ├── 原始数据、处理数据和诊断证据
   └── 分析结果、图表和研究报告
```

## 2.2 四层职责

### 用户交互层

负责人与 Agent 之间的信息交换。Native Chat 承担开放式讨论；AUQ
承担需要明确答案的结构化交互。两者共享同一科研上下文，不得形成两套互相冲突的决策记录。

### PFC Interaction Core

负责持续讨论、上下文维护、决策管理和工作流协调。Core 不替代专业模块的
PFC 科研知识，也不替代 Itasca MCP/Bridge 的执行能力。

### 科研工作流与专业能力层

科研工作流定义研究人员正在完成什么工作；专业模块提供完成该工作的专业能力。一个阶段可以调用一个或多个模块，同一个模块也可以服务于多个阶段。

### 工具与执行层

Itasca MCP/Bridge 负责工具访问和 PFC 执行；PFC
负责数值计算；Visualization Skill 负责科研可视化。PFC Interaction
不重复实现这些底层能力。

## 2.3 阶段、模块与工具的关系

必须严格区分：

-   **阶段（Stage）：** 研究人员当前正在推进的科研工作。
-   **模块（Module）：** Agent 为完成当前工作调用的专业能力。
-   **工具（Tool）：** 模块执行具体操作时使用的外部能力。
-   **交互事件（Interaction）：**
    需要研究人员提供信息、判断、确认或授权的时刻。

不得将"进入
M2"直接等同于"向用户提问"，也不得将"某阶段完成"简单等同于"某模块调用成功"。

# 三、科研工作流：六个核心阶段

六个阶段是用户可见的科研工作主线，但不是不可逆的固定流水线。阶段可以循环、回退、并行准备或根据研究任务跳过不适用的内容。Agent
必须说明跳过某项工作的原因。

## 3.1 阶段一：研究对象与科研目标

**核心问题：研究什么、为什么研究、需要回答什么科学问题？**

主要工作：

1.  识别研究对象、材料、结构或物理过程；
2.  明确研究背景、研究意义和实际问题；
3.  提炼核心科学问题；
4.  明确研究目的和预期回答；
5.  梳理已有研究、已有模型和可用资料；
6.  提出可讨论的研究假设；
7.  识别自变量、因变量、控制变量和约束；
8.  明确研究范围、适用边界和预期成果；
9.  判断研究问题是否适合采用 PFC 数值模拟。

Agent
应当主动帮助用户完善研究问题，而不是只抽取关键词。对研究目标存在多种解释时，应展示不同解释及其影响，邀请用户讨论。

**阶段输出：**

-   `research_brief.md`：研究对象、背景、意义和目的；
-   `research_question.md`：科学问题；
-   `research_hypotheses.md`：研究假设及其状态；
-   `research_scope.md`：研究范围和约束；
-   `research_requirements.json`：结构化研究要求。

**阶段完成条件：**

研究对象、核心目标、主要科学问题和研究边界已经足以指导实验设计；尚未解决的假设和不确定性已被明确记录；用户同意进入实验设计，或明确要求继续讨论。

## 3.2 阶段二：实验类别与实验设计

**核心问题：通过什么实验回答研究问题？需要哪些工况和对照？**

主要工作：

1.  识别适用的 PFC 数值实验类别；
2.  讨论实验类型和选择依据；
3.  确定是否需要对照组、基准组或空白组；
4.  确定自变量、控制变量和响应指标；
5.  选择单因素、多因素、正交、全因子或其他适用设计；
6.  确定工况数量、参数组合和重复试验需求；
7.  识别混杂因素和不可归因风险；
8.  设计观测指标、数据采集计划和比较方法；
9.  检查实验方案是否能够回答阶段一提出的科学问题。

实验类型不能只按名称套用模板。例如单轴压缩、三轴压缩、巴西劈裂、直剪、结构面剪切、颗粒流动、边坡稳定和颗粒破碎等实验，应根据研究目标确定具体方案。

**对照组设计要求：**

-   说明是否需要对照组；
-   说明对照组用于排除或识别什么影响；
-   说明基准条件及其科学意义；
-   说明试验组与对照组之间允许变化的因素；
-   不需要对照组时，也必须说明理由。

**阶段输出：**

-   `experiment_design.md`：实验设计说明；
-   `experiment_matrix.csv`：工况矩阵；
-   `variable_schema.json`：变量体系；
-   `control_groups.md`：对照组和基准组说明；
-   `measurement_plan.md`：观测指标与数据采集计划。

**阶段完成条件：**

实验类型、工况逻辑、变量关系、对照策略、观测指标和比较方法明确；实验设计与研究问题之间存在可解释的对应关系；重要设计选择经过用户确认。

## 3.3 阶段三：技术方案与建模路线

**核心问题：如何将实验设计转化为科学上合理、技术上可执行的 PFC 模型？**

主要工作：

1.  确定 PFC2D 或 PFC3D 及其选择依据；
2.  讨论模型几何、试样尺寸和颗粒生成方式；
3.  讨论粒径、级配、颗粒数量和计算规模；
4.  选择接触模型及其适用依据；
5.  设计细观参数体系和参数来源；
6.  确定墙体、边界条件和加载装置；
7.  确定加载、伺服和停止条件；
8.  确定应力、应变、裂纹、位移、接触网络等测量方式；
9.  设计数据采集频率和输出格式；
10. 制定模型初始化、平衡和验证方案；
11. 评估计算成本、数值限制和模型简化的影响。

技术方案必须说明选择依据、适用条件、替代方案和已知局限。Agent
不得把某个常用接触模型或参数组合当作所有研究问题的默认答案。

**建模验证至少区分：**

-   语法与命令检查；
-   模型结构检查；
-   初始状态和平衡检查；
-   参数与边界条件一致性检查；
-   物理合理性检查；
-   PFC 实际运行验证。

脚本生成成功不代表模型已验证；模型能够运行也不代表模型具有科学有效性。

**阶段输出：**

-   `technical_route.md`：技术方案及选择依据；
-   `model_design.md`：模型设计；
-   `model_requirements.json`：建模要求；
-   `measurement_schema.json`：测量和输出定义；
-   `model_validation_plan.md`：模型验证计划。

**阶段完成条件：**

模型维度、几何、接触模型、边界、加载、测量和验证路线已明确；关键假设和技术选择得到确认；具备生成模型的条件。

## 3.4 阶段四：参数确定与标定

**核心问题：参数从哪里来、如何确定、如何证明其能够产生目标宏观响应？**

参数确定与标定是 5.0
必须重点建设的跨模块工作流，不得将其简化为一次性填写参数表。

主要工作分为六类：

### A. 参数分类与来源识别

-   颗粒与材料基本参数；
-   接触模型类型及其参数；
-   试样与几何参数；
-   边界和加载参数；
-   数值计算控制参数；
-   数据采集和分析参数。

每个参数应记录名称、物理意义、单位、取值、范围、来源、依据、适用条件和确认状态。参数来源应区分实验测定、文献、已有模型、经验估计、反演标定和用户指定。

### B. 初始参数确定

根据研究目标、实验资料、材料性质和 PFC 模型要求提出初始参数。Agent
应说明参数依据和不确定性，不得将缺乏来源的估计值描述为已知事实。

### C. 宏细观参数标定

围绕目标宏观响应设计标定流程。例如：

1.  明确目标宏观指标及目标曲线；
2.  确定标定实验和基准工况；
3.  选择待标定的细观参数；
4.  确定参数调整范围和约束；
5.  运行标定工况；
6.  计算模拟结果与目标结果的误差；
7.  分析参数影响及可能的非唯一性；
8.  调整参数并重复计算；
9.  判断是否达到预设标定标准；
10. 保存最终参数、误差和标定证据。

标定指标必须由研究任务确定，不得默认所有实验都使用相同指标或误差阈值。

### D. 参数敏感性与耦合分析

识别对目标响应影响显著的参数，判断参数之间是否存在耦合。必要时调整标定顺序或增加实验工况，避免仅凭单一曲线拟合就宣称参数具有唯一性。

### E. 参数确认与版本管理

参数必须区分：

-   用户提供；
-   Agent 建议；
-   待标定；
-   标定中；
-   已标定；
-   已确认；
-   已用于正式仿真；
-   已废弃或被新版本替代。

任何关键参数变更都应关联变更原因、影响范围、对应模型版本和重新计算要求。

### F. 标定失败与返回机制

当标定无法满足目标时，Agent
不得无限制地自动调参。应分析可能原因，例如模型结构不适配、目标数据不完整、参数不可辨识、参数范围不合理或测量口径不一致，并提出下一步验证建议。涉及模型假设变化时必须返回阶段三讨论。

**跨模块职责：**

-   M2：定义参数研究变量、参数范围、标定工况和试验矩阵；
-   M3：实现参数配置、模型构建和模型修改；
-   M4：执行标定工况并管理运行任务；
-   M5：诊断异常、检查模型和数值可信度；
-   M6：计算目标指标、误差、敏感性和对比结果；
-   Core：组织讨论、维护参数状态、协调迭代并管理用户决策。

**阶段输出：**

-   `parameter_register.csv`：参数登记表；
-   `parameter_sources.md`：参数来源与依据；
-   `calibration_plan.md`：标定方案；
-   `calibration_matrix.csv`：标定工况矩阵；
-   `calibration_history.csv`：标定迭代记录；
-   `calibration_results.json`：标定指标和误差；
-   `calibrated_parameters.json`：已确认参数及版本；
-   `parameter_change_log.md`：参数变更记录。

**阶段完成条件：**

参数来源、单位、取值和状态明确；适用的标定流程已执行并记录；标定结果达到用户或研究方案预先确定的标准，或明确记录未达到标准及其原因。未经验证的参数不得标记为已标定。

## 3.5 阶段五：仿真执行与异常干预

**核心问题：如何可靠执行仿真，并在异常发生时及时控制和处理？**

主要工作：

1.  创建仿真任务和工况；
2.  检查执行环境与模型版本；
3.  调用现有 Itasca MCP/Bridge 工具链；
4.  执行 PFC2D/PFC3D 脚本；
5.  管理单工况、多工况和批量任务；
6.  获取运行状态、日志和输出文件；
7.  根据预先定义的规则执行检查点；
8.  发现异常时暂停、停止或隔离任务；
9.  调用科学诊断能力分析异常；
10. 根据用户决策执行修正、恢复或重跑；
11. 检查数据完整性并保存运行证据。

### 运行控制与科学诊断必须分离

**M4 Simulation Management：运行控制层**

-   监测任务状态；
-   识别任务失败、超时、中断或完成；
-   执行暂停、停止、恢复和重跑；
-   管理检查点、日志和任务记录；
-   防止重复执行、错误覆盖和状态误报。

**M5 Scientific Diagnosis：问题诊断层**

-   判断模型设置是否存在问题；
-   判断数值计算是否异常；
-   判断物理行为是否符合研究假设；
-   判断数据是否完整、可信；
-   分析异常原因及可信程度；
-   提出修正建议和复核要求。

M4 是仿真运行的控制与刹车机制，M5 是分析问题的诊断机制。M4
可以根据预先设定的安全规则立即停止任务，但不得擅自将科学异常归因于某个物理原因；M5
提供诊断依据，重大模型变更由用户确认。

**异常等级建议：**

  --------------------------------------------------------------------------------------------------------
  等级                    情况                                           建议动作
  ----------------------- ---------------------------------------------- ---------------------------------
  L0 信息                 正常进度、普通提示                             记录并继续

  L1 警告                 指标偏离预期但尚未达到停止条件                 提示并按策略继续监测

  L2 需判断               可能影响结果可信度                             暂停或到检查点请求诊断/用户决策

  L3 严重                 明确违反安全停止条件、计算失控或关键数据损坏   按预设策略立即停止并保留证据
  --------------------------------------------------------------------------------------------------------

异常阈值必须结合实验类型、计算阶段和物理含义设置，不得用单一阈值覆盖所有
PFC 实验。

**阶段输出：**

-   `simulation_config.json`：仿真配置；
-   `simulation_status.json`：任务状态；
-   `simulation_log/`：运行日志；
-   `checkpoint_manifest.json`：检查点记录；
-   `anomaly_records.json`：异常事件；
-   `execution_report.md`：执行报告；
-   `simulation_artifacts/`：原始仿真产物。

**阶段完成条件：**

任务状态有实际工具证据；应执行的工况已完成或明确标记失败、取消和未完成；输出文件通过完整性检查；异常处理和重跑记录可追溯。

## 3.6 阶段六：结果分析与科研总结

**核心问题：得到了什么结果，结果是否可信，能够支持什么结论？**

主要工作：

1.  识别和读取 PFC 原始输出；
2.  建立原始数据清单和完整性检查；
3.  统一单位、坐标、时间步和计算口径；
4.  计算实验目标对应的科研指标；
5.  分析应力---应变、位移、裂纹、颗粒运动和接触网络等数据；
6.  比较对照组、试验组和不同参数工况；
7.  开展统计、敏感性和不确定性分析；
8.  检查数据质量和结果稳健性；
9.  将结果与研究假设和已有认识进行比较；
10. 形成有证据支持的科研解释和结论；
11. 判断是否需要返回前序阶段修订研究设计或模型。

### M5 与 M6 的边界

-   M5 判断数据和物理结果是否存在异常、是否具备可信分析条件；
-   M6 在明确的数据口径下计算指标、统计、比较和解释结果。

M6
可以发现结果与预期不一致，但不能仅凭"不符合预期"判定数据错误。需要进一步区分真实物理现象、模型局限、数值问题和数据处理问题。

**可视化职责：**

现有 Scientific Visualization Skill 继续负责科研图表和三维场景展示。M6
提供经过检查的分析数据、指标定义、单位和图表需求，不重复建设可视化引擎。

**阶段输出：**

-   `raw_data_manifest.json`：原始数据清单；
-   `processed_data/`：处理数据；
-   `analysis_config.json`：分析口径和配置；
-   `analysis_results.json`：指标与统计结果；
-   `comparison_report.md`：工况对比；
-   `diagnosis_report.md`：结果可信度及问题记录；
-   `analysis_report.md`：科研分析报告；
-   `research_conclusion.md`：研究结论与局限。

**阶段完成条件：**

关键指标具有明确口径和计算依据；数据质量和结果限制已经说明；结论不超出证据支持范围；用户确认最终科研解释，或明确记录仍需验证的问题。

# 四、六个专业模块的最终职责与边界

六个专业模块继续保留，但其职责以专业能力为边界，不再被视为六个连续的用户交互步骤。

## 4.1 M1：Research Planning------科研规划

**唯一核心职责：定义研究问题和研究目标。**

负责：

-   科研问题识别；
-   研究对象和研究目的整理；
-   科学问题与研究假设梳理；
-   研究范围和边界；
-   研究变量的概念识别；
-   研究路线和预期成果；
-   研究计划完整性检查。

不负责：

-   具体实验矩阵设计；
-   细观参数取值和标定；
-   PFC 脚本生成；
-   仿真运行管理；
-   具体数据指标计算。

输入：用户研究意图、已有资料和研究背景。\
输出：研究问题、目标、假设、范围和研究要求。\
主要协作：M2、M6。

## 4.2 M2：Experiment Design------实验设计

**唯一核心职责：将研究问题转化为可比较、可执行的实验设计。**

负责：

-   实验类型选择；
-   自变量、因变量和控制变量设计；
-   对照组与基准组设计；
-   单因素、多因素和其他实验设计方法；
-   参数研究范围与工况矩阵；
-   重复试验和敏感性分析计划；
-   测量指标和数据采集计划；
-   参数标定工况设计。

不负责：

-   PFC 模型脚本实现；
-   细观参数的实际模型配置；
-   仿真任务执行；
-   数据指标的最终计算。

输入：研究目标、研究假设和实验约束。\
输出：实验方案、变量体系、参数矩阵和测量计划。\
主要协作：M1、M3、M6。

## 4.3 M3：PFC Modeling------数值建模

**唯一核心职责：将已讨论确认的技术方案和实验条件转化为 PFC 模型。**

负责：

-   PFC2D/PFC3D 模型结构设计；
-   几何和颗粒生成；
-   粒径、级配和颗粒分布；
-   接触模型与参数配置；
-   边界、加载和伺服机制；
-   FISH/Python/PFC 命令脚本生成；
-   模型初始化、平衡和结构检查；
-   模型版本及变更记录。

不负责：

-   决定研究目标；
-   独立决定实验设计；
-   独立宣称细观参数标定成功；
-   仿真任务调度和恢复；
-   最终科研结论。

输入：实验设计、技术方案、参数登记表。\
输出：模型脚本、模型配置、模型清单和验证记录。\
主要协作：M2、M4、M5、M6。

## 4.4 M4：Simulation Management------仿真管理

**唯一核心职责：管理 PFC 仿真任务的执行生命周期。**

负责：

-   任务创建和执行环境识别；
-   调用现有 PFC 工具链；
-   单工况和批量工况执行；
-   运行状态与进度管理；
-   检查点管理；
-   暂停、停止、恢复和重跑；
-   日志、文件和运行证据管理；
-   任务状态与输出完整性检查。

不负责：

-   重新实现 PFC 底层执行能力；
-   代替 M5 进行科学原因诊断；
-   擅自修改研究假设和模型参数；
-   代替 M6 计算科研指标。

输入：已验证模型、仿真配置、执行授权。\
输出：任务状态、运行记录、检查点和仿真产物。\
主要协作：M3、M5、M6。

## 4.5 M5：Scientific Diagnosis------科学诊断

**唯一核心职责：判断模型、数值过程、物理行为和数据结果是否存在问题，并提供有证据的诊断。**

负责：

-   模型设置诊断；
-   初始状态诊断；
-   数值稳定性和收敛性诊断；
-   物理行为合理性诊断；
-   数据质量诊断；
-   异常原因分析；
-   诊断可信度和不确定性说明；
-   修正建议和重新验证条件。

不负责：

-   实际控制仿真任务生命周期；
-   代替用户决定重大科学假设；
-   代替 M6 完成全部指标计算和统计分析；
-   把单一阈值异常直接认定为物理错误。

输入：模型、运行状态、日志、原始数据和研究假设。\
输出：诊断报告、异常证据、修正建议和复核计划。\
主要协作：M3、M4、M6、M1。

## 4.6 M6：Scientific Analysis------科学分析

**唯一核心职责：将可信、口径明确的仿真数据转化为可复核的定量结果和科研解释。**

负责：

-   数据读取、整理和单位统一；
-   应力---应变及其他指标计算；
-   力学参数计算；
-   裂纹、颗粒运动和接触网络分析；
-   多工况对比；
-   统计、敏感性和不确定性分析；
-   结果质量检查；
-   研究假设对照和结果解释；
-   为 Visualization Skill 提供数据与图表需求。

不负责：

-   PFC 原始数据采集机制的重复实现；
-   仿真运行控制；
-   代替 M5 进行全面科学诊断；
-   在证据不足时生成确定性结论。

输入：原始数据、诊断信息、分析目标和指标口径。\
输出：处理数据、指标、比较结果和科研分析报告。\
主要协作：M5、M1、M2、Visualization Skill。

# 六、PFC Interaction Core：持续科研讨论引擎

## 6.1 核心定位

Core 是 5.0
的关键基础能力。它不仅负责任务协调、用户授权和状态管理，还必须负责持续主持科研讨论。

Core 不应成为一个庞大的独立科研知识库，也不应取代 Agent
本身的推理能力。其职责是为 Agent
提供稳定的科研上下文、讨论状态、决策记录和工作流约束，使 Agent
能够围绕同一个研究任务持续推进。

## 6.2 五项核心内部能力

### A. Context Manager------科研上下文管理

维护：

-   当前研究任务和研究阶段；
-   用户明确提供的研究事实；
-   已确认的研究目标和假设；
-   实验方案和参数版本；
-   已讨论、已否决和待确认事项；
-   模型、仿真和分析资产；
-   历史决策及其依据；
-   当前未解决问题和约束。

必须区分用户事实、Agent
建议、工具证据和推断，不得把建议自动写成用户决定。

### B. Discussion Manager------持续讨论管理

维护：

-   当前讨论主题；
-   当前讨论要解决的具体问题；
-   已讨论的论点和证据；
-   用户的意见和修改要求；
-   尚未解决的分歧；
-   已比较的备选方案；
-   下一步最有价值的讨论方向；
-   当前阶段是否具备结束条件。

讨论管理不能退化为固定问答清单。讨论主题应根据用户回答和研究问题动态变化。

### C. Reasoning & Proposal------分析与方案建议

Agent 应能够：

1.  分析用户提出的观点；
2.  识别观点中的前提和隐含假设；
3.  发现实验设计中的逻辑冲突；
4.  主动提出可能遗漏的变量和风险；
5.  提出可行的替代方案；
6.  比较不同方案的优缺点和适用条件；
7.  说明需要哪些证据才能判断；
8.  根据用户反馈修改建议。

Agent 不得为了表现主动性而无依据地反驳用户，也不得把推测描述为确定结论。

### D. Decision Manager------科研决策管理

记录：

-   决策主题；
-   决策内容；
-   决策提出者；
-   决策依据；
-   用户确认状态；
-   适用范围；
-   影响的实验、参数和模型版本；
-   决策时间和变更历史。

决策状态建议：

-   `PROPOSED`：Agent 提出建议；
-   `DISCUSSING`：正在讨论；
-   `CONFIRMED`：用户确认；
-   `REJECTED`：用户否决；
-   `DEFERRED`：暂缓决定；
-   `SUPERSEDED`：被新决策替代；
-   `INVALIDATED`：因条件变化而失效。

### E. Workflow Orchestrator------科研工作流协调

负责：

-   判断当前阶段；
-   判断前置条件；
-   选择调用哪些模块；
-   判断是否需要用户参与；
-   判断是否需要 AUQ；
-   管理阶段进入、完成、回退和重开；
-   根据结果分析触发前序阶段重新讨论；
-   确保未经授权的高影响操作不执行。

## 6.3 科研讨论的标准循环

``` text
理解用户当前意图
       │
       ▼
读取当前科研上下文
       │
       ▼
确定本轮讨论要解决的问题
       │
       ▼
分析现有信息、假设和证据
       │
       ▼
形成分析、建议、反例或备选方案
       │
       ▼
与用户进行开放式讨论
       │
       ▼
理解用户反馈及其影响
       │
       ▼
更新讨论状态和科研决策
       │
       ▼
判断下一步
   ┌───┼───────────┐
   ▼   ▼           ▼
继续讨论  调用专业模块  阶段性总结
   │   │           │
   └───┴─────┬─────┘
             ▼
       判断阶段完成条件
             │
       ┌─────┴─────┐
       ▼           ▼
     未完成       已完成
       │           │
  继续或返回     进入下一阶段
```

## 6.4 讨论深度与阶段推进规则

不得设置"每阶段提问 3 个问题"或"回答完 5 个问题自动完成"等固定规则。

Agent 应根据以下条件决定是否继续讨论：

-   是否存在影响研究结论的关键未知条件；
-   是否存在多个尚未比较的技术方案；
-   是否存在未经验证的核心假设；
-   是否存在实验设计中的变量混杂；
-   是否存在用户与 Agent 的意见分歧；
-   是否存在影响模型有效性的参数或边界问题；
-   是否已经具备进入下一阶段的必要条件。

如果用户明确要求先给出初步方案，Agent
可以在不完整信息下给出暂定方案，但必须标记假设、风险和待确认项。

如果用户暂时无法提供信息，Agent
应提出合理的备选处理方式，例如暂定范围、敏感性分析或后续验证，而不是反复追问同一个问题。

## 6.5 阶段总结不是讨论终止

每个阶段可以形成阶段性总结，但总结应保留：

-   已确认内容；
-   Agent 建议但未确认内容；
-   尚未解决问题；
-   当前采用的假设；
-   可能影响后续工作的风险；
-   下一阶段的前置条件。

用户可以随时修改已确认内容。修改后，Core
必须识别受影响的后续决策和资产，并标记需要重新检查的内容，不能无条件沿用旧审批。

# 七、Agent Native Chat 与 AUQ 双通道交互规范

## 7.1 通道定位

### Agent Native Chat：默认交互通道

适用于：

-   研究问题讨论；
-   科研思路梳理；
-   技术方案论证；
-   参数标定策略讨论；
-   方案比较；
-   结果解释；
-   用户提出异议和修改要求；
-   需要连续上下文的多轮协商。

Native Chat 不应被固定问题列表限制。

### AUQ：结构化辅助交互通道

适用于：

-   参数选择；
-   多项条件确认；
-   实验工况选择；
-   结构化信息补充；
-   检查点决策；
-   异常处理选择；
-   批量任务审批；
-   需要异步等待和明确答案的事项。

AUQ 只负责呈现问题和收集回答，不负责独立完成科研推理，也不直接获得 PFC
执行授权。

## 7.2 通道选择规则

  场景                           默认方式       原因
  ------------------------------ -------------- ------------------------
  研究意义和科学问题             Native Chat    需要开放讨论
  实验类型比较                   Native Chat    需要解释不同路线
  对照组必要性                   Native Chat    需要讨论科学逻辑
  接触模型的适用性               Native Chat    涉及专业假设和论证
  多个已明确参数的批量填写       AUQ            适合结构化收集
  多工况方案最终确认             AUQ 或 Chat    根据复杂程度选择
  运行、覆盖、重置等高影响操作   明确授权交互   必须说明影响范围
  异常原因分析                   Native Chat    需要解释证据和不确定性
  异常处理动作确认               AUQ 或 Chat    需要明确用户决策

## 7.3 交互卡片强制设计要求

结构化提问卡片应简洁、美观、逻辑清晰：

1.  一张卡片聚焦一个明确决策主题；
2.  标题应表达需要决定的事项；
3.  说明提供必要背景和影响，不堆砌长篇解释；
4.  选项应互斥、可理解，并在必要时提供"其他"或自定义输入；
5.  展示单位、范围、默认值和依据；
6.  对高影响决策明确标识影响范围；
7.  默认不同时呈现多个无关问题；
8.  用户可以在适用情况下跳过或暂缓；
9.  用户回答后，Agent 必须解释该回答对方案的影响；
10. 卡片回答不能自动等同于执行授权。

## 7.4 双通道一致性

Native Chat 和 AUQ 必须共享统一的决策记录：

-   同一个决策只能有一个有效状态；
-   AUQ 回答应回写科研上下文；
-   Chat 中用户修改决定时，应使冲突的旧选择失效；
-   不得重复询问已经明确回答且条件未变化的问题；
-   不得把 AUQ 的"选择某参数"解释为"批准执行整个仿真"；
-   不得因通道切换丢失讨论历史。

## 8.4 统一证据类型

所有模块必须区分：

1.  `USER_INPUT`：用户明确提供的信息；
2.  `AGENT_PROPOSAL`：Agent 提出的建议；
3.  `TOOL_EVIDENCE`：PFC 或其他工具实际返回的信息；
4.  `COMPUTED_RESULT`：基于原始数据计算得到的结果；
5.  `INFERENCE`：Agent 基于现有证据作出的推断；
6.  `UNVERIFIED_ASSUMPTION`：尚待验证的假设。

## 8.5 统一模块接口

每个模块至少定义：

  字段                  含义

  Task ID               所属科研任务
  Stage                 触发该模块的科研阶段
  Input                 输入内容及来源
  Preconditions         前置条件
  Execution             执行过程
  Output                结构化结果
  Evidence              依据和证据
  Status                模块状态
  Decisions             需要用户决策的事项
  Limitations           已知限制
  Affected Assets       可能影响的科研资产

模块输出必须能被后续模块读取，不得只返回一段不可解析的自然语言总结。

# 九、科研阶段状态与决策授权

## 9.1 阶段状态

建议阶段状态：

-   `NOT_STARTED`：尚未开始；
-   `DISCUSSING`：正在讨论；
-   `IN_PROGRESS`：正在执行阶段工作；
-   `WAITING_FOR_USER`：等待用户决策；
-   `READY_FOR_REVIEW`：阶段内容已形成，等待审核；
-   `COMPLETED`：满足阶段完成条件；
-   `BLOCKED`：存在阻塞条件；
-   `REOPENED`：已完成阶段因新信息重新打开；
-   `CANCELLED`：用户取消。

阶段状态与模块任务状态相互独立。一个阶段可以包含多个模块调用和多轮讨论。

## 9.2 模块任务状态

保留并统一 4.0 的任务状态思想：

-   `NOT_STARTED`
-   `READY`
-   `RUNNING`
-   `WAITING_FOR_USER`
-   `COMPLETED`
-   `FAILED`
-   `BLOCKED`
-   `CANCELLED`

任务完成不代表科学结论已验证。

## 9.3 讨论、确认与授权的区别

必须严格区分：

-   **讨论（Discussion）：** 用户和 Agent 分析科研问题，不产生执行授权。
-   **方案确认（Confirmation）：**
    用户确认研究假设、实验方案、参数或模型设计。
-   **执行授权（Authorization）：** 用户明确允许执行具有实际影响的操作。
-   **实际执行（Execution）：** 工具真实执行并返回证据。
-   **科学验证（Validation）：** 对模型、数据或结果进行相应验证。

任何一个状态都不能自动替代另一个状态。

## 9.4 授权规则

需要明确授权的操作包括但不限于：

-   启动正式仿真；
-   覆盖已有模型或结果；
-   重置或删除模型状态；
-   批量执行大量工况；
-   修改已确认的关键参数并重新计算；
-   取消或中断正在运行的重要任务。

用户确认一个实验方案，不等于授权执行所有相关任务。审批必须绑定具体任务、对象、版本和操作范围。

## 9.5 审批失效

出现以下情况时，旧审批应重新评估：

-   模型版本变化；
-   关键参数变化；
-   实验矩阵变化；
-   执行对象或操作范围变化；
-   研究假设变化；
-   任务状态变化导致原操作不再适用。

批准状态不等于执行成功。只有获得实际工具执行证据后，才能更新执行状态。

# 十、异常发现、刹车与科学诊断闭环

## 10.1 异常处理流程

``` text
M4 监测仿真状态
       │
       ▼
发现异常或触发检查点
       │
       ▼
判断是否达到预设停止条件
   ┌───┴───────────┐
   ▼               ▼
达到停止条件      未达到停止条件
   │               │
停止/暂停任务      继续监测或记录警告
   │
   ▼
保存日志、状态和数据证据
   │
   ▼
M5 分层诊断
   │
   ▼
生成原因分析和修正建议
   │
   ▼
Core 组织用户讨论
   │
   ▼
用户决定处理路线
   │
   ▼
M3 修改模型/参数，或 M4 恢复/重跑
   │
   ▼
重新验证并记录结果
```

## 10.2 诊断层级

  层级     检查对象         典型问题
  -------- ---------------- --------------------------------
  模型层   模型结构和参数   接触模型错误、边界设置不合理
  数值层   计算过程         不稳定、异常振荡、计算发散
  物理层   物理行为         破坏模式与研究假设不符
  数据层   输出数据         缺失、重复、异常值、单位不一致
  结果层   科研解释         证据不足、结论超出数据支持范围

## 10.3 诊断输出

每个诊断项应包括：

-   问题描述；
-   发现时间和对应任务；
-   发现依据；
-   关联日志、数据和模型版本；
-   可能原因；
-   原因可信程度；
-   建议处理措施；
-   是否需要用户确认；
-   是否建议停止、恢复或重新计算；
-   修正后的复核条件。

必须区分已确认原因、可能原因和待验证假设。

# 十一、与现有工具和 Skill 的关系

## 11.1 Itasca MCP / Bridge

继续承担 PFC 工具访问、命令执行和状态获取等底层职责。

PFC Interaction 不重复实现：

-   PFC 命令执行器；
-   Bridge 服务；
-   PFC 底层 API；

M4 负责组织和管理调用，不应重新实现底层执行能力。

## 11.2 PFC2D / PFC3D

负责真实数值计算。模型和仿真是否成功，必须以实际 PFC 环境执行证据为准。

## 11.3 Scientific Visualization Skill

继续负责：

-   科研图表；
-   曲线、热图、玫瑰图、雷达图等适用图表；

## 11.4 AUQ

继续作为结构化交互辅助能力。它不负责科研语义理解、开放式讨论主持、专业判断或
PFC 执行。

## 11.5 Agent Harness

PFC Interaction 应尽量适配不同 Agent Harness。Skill
提供工作流规则、专业知识、决策约束和工具使用规范；不应把核心科研能力绑定到单一
Agent 平台。

# 十二、实施路线与优先级

5.0 不建议一开始同时开发六个完整模块。应先解决 Core
和科研工作流问题，再逐步扩展专业能力。

## 12.1 第一阶段：架构与科研讨论基础（P0）

目标：让 Agent 能够持续主持科研讨论，并维护统一科研上下文。

建设内容：

1.  重构六阶段科研工作流；
2.  冻结六个模块的职责边界；
3.  建立统一科研任务和决策数据结构；
4.  建立 Context Manager；
5.  建立 Discussion Manager；
6.  建立 Reasoning & Proposal 规则；
7.  建立 Decision Manager；
8.  建立 Workflow Orchestrator；
9.  明确 Native Chat 与 AUQ 的职责；
10. 建立阶段完成和回退规则。

验收重点：

-   多轮讨论能够延续上下文；
-   Agent 不会问完少量固定问题就自动结束；
-   用户修改决定后，相关后续方案能够被识别为受影响；
-   Agent 能主动提出有依据的建议和风险；
-   不会把 Agent 建议误记为用户决定。

## 12.2 第二阶段：科研规划、实验设计与技术方案（P1）

目标：完成从科研问题到可执行建模要求的前端流程。

建设内容：

-   M1 Research Planning；
-   M2 Experiment Design；
-   M3 PFC Modeling；
-   对照组和工况矩阵；
-   技术方案比较；
-   模型检查和实际 PFC 验证。

验收案例：

从一个不完整的研究想法出发，经过持续讨论，形成研究计划、实验设计、工况矩阵、技术方案和可在真实
PFC 环境验证的模型。

## 12.3 第三阶段：参数确定与标定闭环（P1，重点专项）

目标：建立跨模块参数标定能力。

建设内容：

-   参数来源和参数登记；
-   标定目标与误差口径；
-   标定工况矩阵；
-   模型参数配置；
-   标定运行任务；
-   误差计算和敏感性分析；
-   参数调整和版本管理；
-   标定结果确认。

验收案例：

使用目标宏观力学性质和基准实验，完成至少一个有明确目标、误差指标、参数调整记录和独立复核的标定流程。不能只验证参数表生成成功。

## 12.4 第四阶段：仿真管理与异常干预（P2）

目标：完成真实仿真执行和可控异常处理。

建设内容：

-   M4 Simulation Management；
-   运行状态和检查点；
-   暂停、中断、恢复和重跑；
-   M5 Scientific Diagnosis；
-   异常证据和诊断报告；
-   用户决策与修正闭环。

验收案例：

在真实 PFC
环境中执行任务，触发可复现的异常或检查点，验证状态识别、证据保存、用户决策、修正和重跑。

## 12.5 第五阶段：科学分析与研究总结（P2）

目标：形成从真实仿真数据到可复核科研结论的能力。

建设内容：

-   M6 Scientific Analysis；
-   数据完整性和单位检查；
-   指标计算与独立复核；
-   多工况对比；
-   结果解释；
-   Visualization Skill 集成；
-   研究总结与报告输出。

验收案例：

使用真实 PFC
输出完成数据读取、指标计算、工况比较、图表生成和有证据支持的研究结论。

# 十三、5.0 总体验收体系

5.0 不以模块数量、Skill
文件数量或问题卡片数量作为完成标准。必须通过完整科研案例检验实际能力。

## 13.1 交互验收

  编号   验收内容       通过标准
  ------ -------------- -----------------------------------------------
  I-01   模糊研究意图   Agent 能主动澄清并提出研究方向
  I-02   多轮讨论       能围绕同一问题持续讨论，不机械重复提问
  I-03   用户修改意见   能理解修改对既有方案的影响
  I-04   主动建议       能提出有依据的方案、风险和反例
  I-05   方案比较       能比较不同方案及其适用条件
  I-06   讨论状态       能区分已确认、待讨论、被否决和暂缓事项
  I-07   阶段推进       根据完成条件推进，而非按固定问题数量推进
  I-08   阶段回退       能返回前序阶段并识别受影响内容
  I-09   双通道一致性   Native Chat 与 AUQ 不重复询问、不产生冲突决策
  I-10   授权边界       讨论、确认和执行授权严格区分

## 13.2 科研流程验收

  编号   验收内容   通过标准
  ------ ---------- ------------------------------------
  W-01   研究目标   形成清晰研究对象、目标和问题
  W-02   实验设计   变量、对照组和工况逻辑合理
  W-03   技术方案   模型、边界、加载和测量方案有依据
  W-04   参数确定   参数来源、单位、范围和状态可追溯
  W-05   参数标定   能形成实际迭代和误差评价闭环
  W-06   模型验证   区分脚本生成、实际运行和科学验证
  W-07   仿真管理   真实任务状态、检查点和恢复行为正确
  W-08   异常诊断   诊断结论有证据并区分不确定性
  W-09   数据分析   指标计算口径明确且可独立复核
  W-10   研究总结   结论不超出数据和模型的支持范围

## 13.3 工程验收

-   模块接口和版本明确；
-   科研任务、阶段和模块状态不混用；
-   用户决策可追溯；
-   模型、参数、仿真和分析资产有关联；
-   失败、取消、超时和重试状态正确；
-   旧审批在关键条件变化后失效；
-   不重复执行或覆盖未经确认的成果；
-   PFC 工具调用具有真实执行证据；
-   不把工具返回成功等同于科学验证成功。

## 13.4 完整端到端验收案例

建议至少建立以下完整案例：

**案例：PFC3D 岩石单轴压缩与细观参数标定**

要求覆盖：

1.  用户提出初步研究想法；
2.  Agent 与用户讨论研究目标和研究意义；
3.  共同确定实验类别及是否设置基准组；
4.  讨论接触模型、颗粒级配、边界和加载方案；
5.  确定目标宏观指标和参数标定策略；
6.  建立参数登记表和标定工况；
7.  生成模型并在真实 PFC3D 环境验证；
8.  执行标定计算；
9.  比较模拟曲线与目标结果；
10. 讨论参数调整及其影响；
11. 达到预定标准或明确记录未达到的原因；
12. 执行正式工况；
13. 检查异常并完成必要干预；
14. 分析应力---应变、裂纹和破坏特征；
15. 形成结果比较和研究总结；
16. 根据结果判断是否返回前序阶段。

验收必须记录实际对话、阶段状态、决策记录、工具调用证据、模型版本、参数版本、数据文件和最终分析结果。

不能仅凭 Agent 生成了一份完整报告，就判定科研协作闭环通过。

# 十五、建设边界与最终定位

## 15.1 5.0 不建设的内容

为保持轻量实用，5.0 不以以下内容为建设目标：

-   不重复开发 Itasca MCP/Bridge；
-   不重复开发 PFC 执行器；
-   不重复开发 Scientific Visualization Skill；
-   不强制建设独立 Web 前端；
-   不强制建设大型数据库和全栈服务；
-   不将 AUQ 扩展成独立科研 Agent；
-   不将六个模块做成六个必须分别启动的 Agent；
-   不以固定问答模板代替开放式科研讨论。

如果后续真实使用中出现跨会话协作、多人共享、任务队列或资产管理需求，再评估是否需要独立服务、数据库或
Web 界面。

## 15.2 5.0 的最终产品形态

用户面对的是一个持续协作的 PFC 科研助手，而不是六个模块的操作面板。

用户可以自然地提出研究想法，也可以随时补充资料、修改参数、质疑 Agent
的方案、返回之前的研究阶段或要求解释某项决策。

Agent 应当能够：

-   理解研究目标；
-   主持科研讨论；
-   主动提出建议；
-   比较不同实验方案；
-   组织参数确定和标定；
-   调用专业模块；
-   使用现有 PFC 工具链；
-   解释异常和结果；
-   保持完整科研上下文；
-   形成可追溯、可复核的研究成果。

## 15.3 最终定义

**PFC Interaction 5.0
是一个以持续科研讨论为核心、以真实科研工作流为主线、以六项专业科研能力为支撑、以
PFC 工具链为执行基础的轻量化智能科研协作 Skill。**

它的核心价值不在于能够提出多少问题、调用多少模块或生成多少脚本，而在于能否与研究人员共同完成从科研问题提出、实验设计、技术方案论证、参数标定、仿真执行、异常干预到结果分析的完整研究过程。

**5.0 的首要验收标准：研究人员能够与 Agent 围绕一个真实 PFC
科研问题持续讨论，逐步形成有依据的决策，并最终完成可执行、可验证、可追溯的科研工作闭环。**
