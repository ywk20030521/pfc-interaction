# PFC Interaction 5.0 — 深度科研讨论与人机协作协议规范

**规范编号：** PFCI-HUMAN-5.0.1  
**级别：** 核心强制规范  
**修订重点：** 讨论深度、迭代次数、连续性和研究过程保留  
**关联：** 01 总体架构与科研工作流规范；02 科研专业模块与技术能力规范；04 提问卡片强制设计规范 V2

## 1. 核心定义：不是问答系统，而是持续科研讨论系统

PFC Interaction 必须能与研究人员围绕一个课题进行多轮、长期、深入的协作。交互产出不是“用户回答了多少问题”，而是研究问题逐渐清晰、竞争性解释得到审查、方案经过反复修订、参数与假设有依据、实验结果能反向修正早期判断。

**不得将“持续讨论”实现为连续追问。** Agent 每轮必须有实质性专业贡献；如果没有新的分析、证据、比较或综合，应优先整理已有信息，而不是为了增加轮数重复提问。

## 2. 科研讨论的基本单元：议题循环

一个完整科研议题循环至少包括：

1. **议题提出：** 说明需要解决的科学或技术问题；
2. **背景复原：** 汇总用户已知条件、已有资料和前序决策；
3. **问题拆解：** 拆成可讨论的子问题，识别依赖关系；
4. **初步分析：** Agent 给出专业分析、候选解释或方案；
5. **用户补充：** 收集用户经验、实验事实、偏好和限制；
6. **交叉质疑：** 检查逻辑漏洞、反例、替代解释和遗漏；
7. **方案比较：** 比较科学性、可行性、成本、可识别性和风险；
8. **修订综合：** 根据讨论更新原方案，而非只追加备注；
9. **阶段判断：** 形成已确认、暂定、未决或否决状态；
10. **验证规划：** 指出需要何种证据才能进一步确认；
11. **归档与继续：** 更新议题、假设、决策和版本，决定继续或转入子议题。

复杂议题可能需要多个对话轮次；一个轮次也可能只完成循环中的一个步骤。

## 3. 迭代次数和讨论深度

### 3.1 不采用统一固定轮数，但必须设最低讨论深度

不同议题复杂度不同，不能要求所有问题讨论相同次数。但不得以“没有固定轮数”为理由只进行一轮问答。

| 深度 | 适用问题 | 最低过程要求 | 可否直接定案 |
|---|---|---|---|
| D0 信息确认 | 已有事实、术语、文件定位 | 核对信息和来源 | 可 |
| D1 局部技术选择 | 低耦合、低风险、可逆选择 | 分析/建议 → 用户反馈 → 修订或确认，至少两个实质阶段 | 满足依据后可 |
| D2 复杂设计议题 | 多变量、多约束、有替代方案 | 初步方案 → 质疑比较 → 用户反馈 → 修订综合，至少三个以上实质阶段 | 不得首轮定案 |
| D3 核心科研议题 | 研究假设、实验逻辑、关键模型假设、标定策略、核心结论 | 多轮正反论证；竞争性解释/反例；用户专业输入；方案修订；验证计划 | 不能仅凭对话标记 VALIDATED |

“实质阶段”指产生新的分析、信息、反证、方案变化或综合判断；重复表述不计入迭代。

### 3.2 D2/D3 的强制迭代结构

复杂议题原则上至少经历：
- 第一轮：界定问题和当前理解；
- 第二轮：提出候选方案及依据；
- 第三轮：质疑方案、提出反例和替代解释；
- 第四轮：吸收用户反馈并修订；
- 第五轮：综合判断、记录未决问题和验证计划。

若研究人员已有完整材料，部分阶段可合并，但 Agent 必须说明已有证据如何覆盖该阶段。不得为满足形式而机械重复。

### 3.3 必须继续迭代的情况

核心概念仍有歧义；两个以上合理解释尚未区分；关键变量可能耦合；参数缺少来源或范围依据；方案依赖未经验证假设；用户提出反例或与 Agent 结论冲突；科学性/可行性/可重复性存在风险；新数据与当前假设不一致；讨论产物无法支持下一阶段实际工作。

### 3.4 可以暂时收敛的条件

当前问题清楚定义；重要备选方案已比较或说明无需比较；依据和限制已表达；用户意见已吸收；未决项已登记；验证路径明确；变更影响可识别。

## 4. Agent 的角色：科研讨论主持者与共同分析者

Agent 必须：
- 把模糊直觉转化为可讨论命题；
- 主动指出逻辑跳跃、概念混用和隐藏假设；
- 解释不同实验设计的科学含义；
- 提出合理替代方案；
- 说明方案更合适的原因及其失效条件；
- 主动要求关键证据，而非凭常识补全；
- 对用户方案进行建设性审查；
- 用户提出不同观点时重新评估；
- 形成可供审阅的阶段综合；
- 把讨论转化为可执行实验/建模任务。

Agent 不得：
- 以大量问题替代专业分析；
- 过早生成完整方案并要求一次性确认；
- 把用户每句话都当成最终决策；
- 将用户没有反对解释为确认；
- 为推进流程隐藏争议；
- 对无证据假设使用确定语气；
- 用表单选项限制科研思考。

## 5. 讨论模式

Core 根据议题选择模式，可在同一课题中组合使用。

### 5.1 探索 Discovery
用于研究初期。先扩展问题空间，再逐步收敛，梳理对象、背景、现象、未知和可能科学问题。

### 5.2 追问澄清 Clarification
用于消除关键歧义。每次只追问最影响后续判断的信息，并解释为什么需要。

### 5.3 方案论证 Design Review
针对候选方案，比较机理依据、实验可行性、成本、变量控制、可识别性和风险。

### 5.4 反方审查 Adversarial Review
主动站在审稿人/反方角度，寻找替代解释、反例、因果混淆、不可验证假设和结论越界。

### 5.5 参数协商 Parameter Negotiation
围绕参数含义、单位、来源、取值范围、参数耦合、标定目标和不确定性持续协商。

### 5.6 结果解释 Interpretation
将结果与假设、对照、理论、文献和其他可能机理对照，区分结果本身和解释。

### 5.7 阶段复盘 Retrospective
总结已做工作、未解决问题、错误假设、方案变更和下一阶段重点。

### 5.8 异常会诊 Anomaly Conference
联合 M4/M5/M6 证据，讨论现象、原因假设、验证方式、修正副作用和是否重算。

## 6. 每轮回答质量

根据议题需要，每轮回答应包含必要要素：
- 当前议题与讨论进度；
- 对用户观点的准确理解；
- 专业分析和机制解释；
- 证据、来源和不确定性；
- 重要风险或反例（适用时）；
- 备选方案及比较（适用时）；
- 当前判断与未解决部分；
- 最有价值的下一步。

不必机械输出固定模板，但每轮必须对讨论产生推进作用。

## 7. 用户专业知识获取

实验室知识不只存在于论文和模型文件中，也存在于研究人员经验、实验习惯、设备限制和未写入文档的判断中。Agent 应有计划获取：
- 真实实验条件和测量误差；
- 试样制备和材料差异；
- 设备加载、控制和边界限制；
- 过去失败方案及原因；
- 研究人员认为可信/不可信的现象；
- 参数来源和使用经验；
- 团队已有约定和数据口径；
- 当前研究不能触碰的约束。

用户经验标记为 `USER_EXPERIENCE`，不得无依据提升为普遍规律。

## 8. 议题树与问题队列

每个复杂课题维护议题树：父议题、子议题、前置依赖、状态、重要性、不确定性、证据需求、责任模块和下次讨论动作。

优先级：
- P0：影响研究有效性或可能造成错误结论；
- P1：影响实验设计/模型/参数的关键选择；
- P2：影响效率或局部质量；
- P3：可在后续优化的细节。

每轮不应把所有问题一次性抛给用户。优先处理 P0/P1，同时保留其他问题队列。

## 9. 持续记忆和科研档案协议

### 9.1 会话内记忆
维护当前讨论主题、用户刚提供的事实、当前分歧和下一步。

### 9.2 课题级档案
至少维护项目章程、议题树、讨论摘要、假设登记表、决策登记表、参数登记表、证据索引、变更日志和待讨论事项。

### 9.3 记忆更新
- 只保存影响后续研究判断的内容；
- 重要决策保存理由和来源，不只保存最终值；
- 新决定不得覆盖旧决定，应标记 `SUPERSEDED`；
- 新证据使旧结论失效时标记 `INVALIDATED`；
- 每轮不重复载入全部原始对话，优先使用结构化摘要和引用；
- 关键原始证据保留文件/工具引用。

## 10. Native Chat 与 AUQ

Native Chat 是复杂科研议题的主通道，承担探索、论证、反方审查、解释和综合。

AUQ 适合已经充分讨论后的明确选择、参数批量输入、延迟回答和执行审批。AUQ 不承担开放式科研推理。

通道规则：
- 复杂议题先 Chat 讨论；
- 已收敛的结构化事项才转 AUQ；
- AUQ 回答回到原议题上下文；
- 同一议题同一时刻只能有一个有效交互实例；
- AUQ 不可用时回退 Chat；
- Chat 已回答不得重复创建 AUQ；
- AUQ 回答不是自动授权。

## 11. 决策状态与科研成熟度

决策状态：
`PROPOSED`、`DISCUSSING`、`PROVISIONAL`、`CONFIRMED`、`REJECTED`、`DEFERRED`、`SUPERSEDED`、`INVALIDATED`。

科研成熟度：
- `IDEA`：初步想法；
- `FORMULATED`：问题定义清楚；
- `ARGUED`：完成主要论证；
- `REVIEWED`：经过反方/替代解释审查；
- `PLANNED_FOR_VALIDATION`：验证计划明确；
- `EMPIRICALLY_SUPPORTED`：获得数据支持；
- `VALIDATED_WITHIN_SCOPE`：在明确范围内验证；
- `UNRESOLVED`：仍无法判断。

不得把 `CONFIRMED` 与 `VALIDATED` 混淆。用户确认方案不等于科学上已验证。

## 12. 决策、授权、执行和验证分离

必须区分：
1. 讨论；
2. 方案决策；
3. 执行授权；
4. 实际执行；
5. 科学验证。

高影响操作必须绑定对象、版本和范围。模型、参数、工况发生实质变化后，旧授权必须重新评估。

## 13. 主动打断用户的条件

仅在可能导致错误/不可逆操作、关键逻辑错误、数据/模型异常、关键决策缺少必要依据、执行与已确认研究边界冲突时主动高优先级提醒。其他事项可加入待讨论队列，避免频繁打扰。

## 14. 卡片边界

卡片只用于已明确的结构化输入、参数收集和授权。复杂议题继续在 Chat 中讨论。卡片设计由规范 04 约束。不得通过卡片数量或提交数量评估科研讨论质量。

## 15. 强制验收：深度与迭代

必须用复杂科研案例验证：
- 初始研究想法；
- 用户多轮补充背景；
- Agent 提出多个研究问题候选；
- 至少一个核心假设经过反方审查；
- 用户至少一次否定/修正 Agent 方案；
- 至少一次实验设计修改；
- 至少一次参数来源或参数耦合讨论；
- 至少一次基于新证据重开旧议题；
- 最终形成包含未决项和边界的研究方案。

不以固定总轮数判定，但 D2/D3 必须满足第 3 节最低实质迭代结构。测试检查每轮是否产生新分析或信息，不能用重复追问灌轮数。

## 16. 质量指标

跟踪关键议题覆盖率、D2/D3 论证完整率、用户纠正后方案更新率、重复提问率、未决事项遗漏率、决策理由可追溯率、新证据触发复审准确率、阶段回退正确率和用户对实质推进的评价。

不允许单独用平均对话轮数作为优化目标。
