# PFC Interaction 5.0 — 科研专业模块与技术能力规范

**规范编号：** PFCI-MOD-5.0.1  
**级别：** 强制  
**关联：** 01 总体架构与科研工作流规范；03 深度科研讨论与人机协作协议；04 提问卡片强制设计规范 V2

## 1. 本规范解决的问题

M1–M6 不能只是六个“输入—生成文档”的功能模块。它们必须在真实科研工作中提供专业分析、方法论判断、技术实现、结果诊断和跨阶段反馈。

每个模块必须具备：专业知识与方法、议题拆解、方案生成与比较、反例和风险识别、证据需求判断、结构化产物、跨模块接口和可验证完成条件。

模块不是独立 Agent，不建立第二套用户交互体系。所有用户讨论由 Core 统一组织。

## 2. 六模块责任边界

| 模块 | 主责 | 不负责 |
|---|---|---|
| M1 Research Planning | 科学问题、研究假设、研究边界 | 具体工况矩阵、PFC 脚本、执行 |
| M2 Experiment Design | 实验类别、变量、对照、工况和测量设计 | 模型代码、仿真控制、最终结果解释 |
| M3 PFC Modeling | 模型结构、接触模型、边界、脚本和模型检查 | 科学目标决定、运行调度、宣称标定成功 |
| M4 Simulation Management | 执行生命周期、状态、检查点、暂停/恢复/重跑 | 科学归因、参数优化、结论解释 |
| M5 Scientific Diagnosis | 模型/数值/物理/数据异常与可信度 | 实际任务控制、完整统计分析 |
| M6 Scientific Analysis | 指标、统计、工况比较、假设检验和解释 | PFC 执行、全面异常诊断 |

## 3. 模块共同的深度工作模式

复杂议题必须完成以下工作，不得直接输出最终答案：
1. 理解研究目标、用户判断和约束；
2. 拆分子问题并识别依赖；
3. 区分已知、未知和待验证内容；
4. 形成候选方案；
5. 比较科学合理性、技术可行性、成本、可识别性和风险；
6. 形成阶段判断，标记确认/暂定/未决/否决；
7. 设计验证方法；
8. 回写议题、假设、证据、决策和版本。

简单任务不必机械输出八段，但复杂议题不能缺少这些环节。

## 4. M1 Research Planning — 科研规划

### 4.1 主要任务
将研究人员的想法发展为具有科学价值、可检验性和明确边界的研究问题。

### 4.2 必须深入讨论
- 研究对象、尺度和范围；
- 工程问题与科学问题是否混淆；
- 研究动机是解决应用问题、解释机理还是建立方法；
- 已知现象与尚未解释的现象；
- 现有理论/文献可以解释什么、不能解释什么；
- 研究假设是否可证伪；
- 是否存在竞争性假设；
- 哪些观测能够区分这些假设；
- PFC 是否适合回答问题，模型简化会损失什么；
- 研究结论需要达到什么证据等级。

### 4.3 禁止事项
不得把用户方向快速改写成通用计划后结束；不得无证据编造研究空白；不得将工程目标直接当作科学假设；不得只列变量而不解释变量与科学问题的逻辑关系。

### 4.4 输出
`research_brief.md`、`research_question_tree.md`、`hypothesis_register.md`、`scope_and_limitations.md`、`research_route_options.md`、`open_questions.md`。

## 5. M2 Experiment Design — 实验设计

### 5.1 主要任务
把研究问题转化为能够识别变量作用、检验假设并形成可靠比较的实验方案。

### 5.2 必须深入讨论
- 实验类别是否能回答研究问题；
- 对照组/基准组是否必要，能控制哪些因素；
- 自变量、因变量、控制变量、干扰变量关系；
- 参数能否独立变化，是否存在耦合；
- 单因素、多因素、正交、全因子或分阶段设计的适用性；
- 工况数量与计算成本平衡；
- 是否需要重复试验或不同随机种子；
- 观测指标能否区分不同物理机制；
- 是否存在当前设计无法识别的参数；
- 如何避免相关性被误解为因果关系。

### 5.3 每份实验设计必须交付
设计目标及对应科学问题、实验类别选择依据、对照/基准策略及理由、变量定义和单位、工况矩阵及工况差异、测量指标和采集方式、重复性/随机性策略、计算成本等级、设计风险和无法回答的问题、需要用户确认的关键事项。

### 5.4 输出
`experiment_design_rationale.md`、`variable_causal_map.md`、`control_strategy.md`、`experiment_matrix.csv`、`measurement_plan.md`、`design_risk_register.md`。

## 6. M3 PFC Modeling — PFC 建模

### 6.1 主要任务
把实验方案转化为 PFC2D/PFC3D 模型，并确保关键建模假设可追溯。

### 6.2 必须深入讨论
- 2D 与 3D 对研究问题的影响；
- 颗粒尺寸、级配、数量和代表性体积；
- 接触模型的物理意义和适用范围；
- 微观参数与宏观响应关联；
- 接触刚度、摩擦、黏结、强度和阻尼等参数作用；
- 墙体、边界、加载和伺服条件；
- 初始压密、平衡和初始应力状态；
- 时间步、数值稳定性和计算成本；
- 输出指标、采样频率和数据存储；
- 模型简化和数值误差对结论的影响；
- 模型验证策略及基准案例。

### 6.3 检查层级
1. 脚本语法/命令有效性；
2. 对象、几何和边界结构；
3. 颗粒、接触和参数配置；
4. 初始平衡与数值状态；
5. 加载过程和测量口径；
6. 物理行为与预期机制；
7. 真实 PFC 环境执行证据。

生成脚本不等于模型完成；模型运行成功不等于物理有效。

### 6.4 输出
`modeling_rationale.md`、`model_assumptions.md`、PFC 脚本、`model_manifest.json`、`model_validation_report.md`、`data_collection_spec.json`、`model_change_log.md`。

## 7. M4 Simulation Management — 仿真管理

### 7.1 主要任务
管理真实 PFC 仿真任务生命周期，并将运行状态和证据反馈给 Core。

### 7.2 必须具备
环境与版本核验；模型/参数/工况版本核对；任务创建、提交、查询、等待和中断；检查点与阶段监测；任务状态和日志记录；暂停、恢复、重跑和取消；运行产物完整性检查；失败后判断可恢复性；变更后失效结果标记；防止重复运行和未经授权覆盖。

### 7.3 主动监测
监测频率由实验阶段、风险和计算成本决定。不得每个 cycle 高频向用户发送消息。可采用关键阶段、指标阈值、异常、用户指定检查点和周期摘要。内部监测触发与用户消息触发分离：Agent 可以检查，但只在有价值时汇报。

### 7.4 输出
`simulation_plan.json`、`task_manifest.json`、`checkpoint_log.md`、`execution_log`、`anomaly_event.json`、`execution_report.md`。

## 8. M5 Scientific Diagnosis — 科学诊断

### 8.1 主要任务
对异常、反常结果和数据可信度开展有证据的分层诊断。

### 8.2 诊断报告必须包含
现象描述、发生阶段/时间、实际观测证据、预期行为、偏差程度、可能原因列表、各原因支持/反对证据、待补充证据、诊断置信度、建议验证实验、修正方案及副作用、是否需要回退模型/参数/实验设计。

### 8.3 诊断原则
不得把单一阈值当作所有实验的科学判断。必须结合模型类型、加载阶段、边界条件、物理量趋势、能量、接触状态、裂纹或其他可用证据。

### 8.4 输出
`diagnosis_report.md`、`cause_hypothesis_matrix.csv`、`diagnostic_evidence.json`、`revalidation_plan.md`、`diagnosis_history.md`。

## 9. M6 Scientific Analysis — 科学分析

### 9.1 主要任务
从可信数据中获得可复核的定量结果，并判断结果对研究假设的支持程度。

### 9.2 必须深入讨论
- 原始数据完整性和单位；
- 指标是否真正对应研究问题；
- 统计处理和数据清洗是否改变物理意义；
- 不同工况是否可比；
- 结果支持、部分支持还是反驳假设；
- 是否存在其他合理解释；
- 结果对参数、随机性和模型假设是否敏感；
- 结论适用范围和外推限制；
- 是否需要补充计算或实验。

### 9.3 输出
`analysis_plan.md`、`processed_data_manifest.json`、`analysis_results.json`、`hypothesis_assessment.md`、`comparison_report.md`、`visualization_spec.json`、`research_conclusion_draft.md`。

## 10. 跨模块责任裁定

| 议题 | 主责 | 参与者 | 边界 |
|---|---|---|---|
| 科学问题 | M1 | Core、用户 | M1 定义问题 |
| 变量操作化 | M2 | M1 | M1 定义科学含义，M2 设计实验变量 |
| 对照与工况 | M2 | M1、M6 | M2 设计，M6 评估指标可区分性 |
| 模型选择 | M3 | M1、M2、M5 | M3 提出实现，M5 诊断实际行为 |
| 参数初值/范围 | M2、M3 | M1、M6 | M2 设计实验参数，M3 配置模型 |
| 参数标定 | Core 组织 | M2–M6、用户 | 跨模块闭环 |
| 运行异常 | M4/M5 | Core、用户 | M4 控制任务，M5 诊断原因 |
| 数据可信度 | M5 | M6 | M5 诊断，M6 使用可信数据 |
| 结果解释 | M6 | M1、用户 | M6 解释，M1 复核科学问题 |
| 可视化 | Visualization Skill | M6 | M6 提供数据语义，不重写渲染器 |

## 11. 参数标定跨模块闭环

参数标定是研究议题，不是“输入参数—运行—自动调参”的脚本任务。

1. M1 明确宏观目标和研究问题；
2. M2 设计标定工况、观测指标和目标数据；
3. M3 确定候选接触模型和可配置参数；
4. Core 与用户讨论参数物理意义、来源和合理范围；
5. M4 执行标定工况；
6. M5 检查模型行为和数据可信度；
7. M6 计算误差、敏感性、参数相关性和多解性；
8. Core 组织讨论误差来自参数、模型结构还是实验设计；
9. 用户确认调整方向；
10. M3 更新模型版本，M4 重算；
11. 使用独立工况或独立指标验证；
12. 记录适用范围、残余误差和局限。

禁止把优化器收敛、单条曲线拟合或单次实验匹配当成标定成功。

## 12. 模块统一输出协议

每个模块结果必须包含：
- 任务和模块标识；
- 输入引用及版本；
- 当前处理议题；
- 使用的方法；
- 候选方案及比较；
- 关键证据；
- 结论及置信程度；
- 未决事项；
- 需要用户决策的事项；
- 对其他资产的影响；
- 下一步建议。

模块不得自行把输出写为用户确认的决定，也不得静默修改其他模块拥有的状态。

## 13. 强制验收

每个模块必须有普通案例、复杂案例、信息缺失案例、冲突案例、反例/失败案例、跨模块接口案例和真实 PFC 证据案例。单元测试通过不代表模块具备科研能力。至少一个端到端复杂课题必须贯通六模块，并经历至少一次基于新证据的方案修订。
