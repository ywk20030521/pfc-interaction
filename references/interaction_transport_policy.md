# 交互通道路由：Native Chat 与 AUQ

## 1. 两条正式通道

| 通道 | 主要职责 | 适用内容 | 用户体验 |
|---|---|---|---|
| Native Chat | 连续交流与语义协商 | 状态汇报、结果解释、科研讨论、开放式问题、方案比较、模糊意图澄清 | Agent 当前聊天界面 |
| AUQ | 结构化与异步信息传递 | 参数收集、单选/多选、明确决策、待办问题、延迟回答、多问题排队 | AUQ 自带 TUI/CLI 入口 |

两条通道都是正式支持的交互方式，服务于不同信息形态。它们不是并列的 Agent 或工作流引擎——Agent 始终负责理解、分析、讨论、决策协调和 PFC 操作。

## 2. 路由规则

1. 需要理解上下文、来回推敲或共同形成判断 → **Native Chat**；
2. 问题已足够明确，答案可表达为选项、数值、短文本或确认 → 可用 **AUQ**；
3. 用户暂不在 Chat 前，且问题需保存稍后回答 → 优先 **AUQ**；
4. 涉及复杂科学判断，不得把讨论压缩成 AUQ 选择题：先在 Chat 讨论，再把已明确的决策项交给 AUQ 收集；
5. 用户在 Chat 中已明确回答的问题，不再重复投递 AUQ；
6. AUQ 不可用时回退 Native Chat，明确说明异步队列不可用，不静默丢弃问题。

## 3. 强制约束

- 一个 `interaction_id` 只绑定一个主通道，禁止 Chat 与 AUQ 同时展示同一问题；
- 通道只负责展示与传递，不拥有实验决策权；
- 所有回答转换为统一的交互语义（见 `interaction_protocol.md`）；
- 通道超时 ≠ 用户拒绝；会话断开 ≠ 问题失效；
- 不把某一宿主专有工具名写进核心协议；通过能力探测适配。

### 3.1 去重判定流程（A6 可执行协议，设计通过 / 运行时待验证）

每次准备向操作者提问前，Agent 必须按顺序执行以下判定，防止 Chat/AUQ 双重打扰。

**事项标识（四字段，缺一不可）**：

```
事项键 = experiment_id + stage_id + 决策主题 + context_version
```

- `context_version`：当前模型状态或实验上下文版本（如 cycle 数、参数版本、plan version）。
- 引入原因：**同一阶段可能出现两次相同主题的问题，但模型状态已变化**。例如第一次问"加载速率"，用户回答后参数又被改动；第二次虽主题相同，但已是新的决策事项。因此**不能仅靠主题判断重复**，必须带上 context_version。

**投递状态（`delivery_status`）**：`UNDELIVERED` / `DELIVERED` / `WAITING_ANSWER` / `ANSWERED` / `CANCELLED` / `EXPIRED` / `SUPERSEDED`。

**判定步骤**：

1. **确定事项键**：按四字段构造，以 `context_version` 区分同主题的新旧事项；
2. **查已记录事项**：该事项键是否已有交互？
   - `ANSWERED` → 不再投递，直接沿用回答（若 context_version 未变）；
   - `WAITING_ANSWER` → 保持原通道提问，不另投 AUQ；
   - `EXPIRED` / `CANCELLED` → 可按当前 context_version 重新发起；
   - **主题相同但 context_version 不同** → 这是新事项，允许重新提问；
3. **查 AUQ 会话**：该事项键是否已有 pending 的 AUQ session？
   - 是 → 用 `get_answered_questions` 查询，不重复创建问题；
4. **确需换通道时标记 SUPERSEDED**：如果原提问需要改走另一通道（如用户离开 Chat），**先将被替代的事项标记为 `SUPERSEDED`，再在新通道创建，并保留两者的关联记录（旧事项键 → 新事项键）**。
   - 注意：**已发到 Native Chat 的消息不一定能真正撤回**，不要假定"撤销"可行；SUPERSEDED 是状态标记与关联记录，不是界面撤回操作；
   - 用户可能在旧通道也已回答，因此关联记录用于检测冲突回答；
5. **记录投递状态**：用四字段事项键 + `delivery_status` 更新对话上下文，后续步骤据此判断。

**失败模式（必须避免）**：

- Chat 已问"是否进入加载"，用户已回答；Agent 又投 AUQ——第 2 步拦截；
- 同主题但模型已变（context_version 不同），Agent 误判为重复而不问——第 1/2 步的 context_version 字段拦截；
- 换通道后旧通道回答到达，与新回答冲突——第 4 步的 SUPERSEDED 关联记录用于识别。

> **状态**：本流程为设计协议（**设计通过**）。A6 的真实运行时验证需在 AUQ MCP 工具于宿主会话生效后执行（见 `pr0/AUQ_CAPABILITY_BASELINE.md` A6/A8）；在此之前不得宣称双通道去重已通过。

## 4. 标识关联

两条通道共享同一个 Agent、实验上下文和决策逻辑。AUQ 的 Session ID（UUID，实测版本 3.4.0）**仅用于定位 AUQ 会话**，不能替代：

- `experiment_id`（PFC 实验）；
- `agent_run_id`（Agent 运行）；
- `itasca_task_id`（itasca-mcp 任务）。

Skill 在需要时维护这些标识之间的关联，避免回答串线到错误实验或阶段。

## 5. 能力探测流程

1. 检查宿主是否提供结构化提问工具（当前宿主已实测可用）；
2. 检查 AUQ 是否安装并在 MCP 配置中注册；
3. 按可用性决定路由能力：
   - 两者可用：按路由规则选择；
   - 仅 Chat：全部走 Chat，声明 AUQ 异步能力不可用；
   - 均无：退化为普通对话文字提问，决策协议不变。
