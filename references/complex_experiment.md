# 复杂模拟实验的协作方法

复杂实验（多阶段、长时、参数交互多）不是靠更强的单点能力，而是靠**结构分解 + 阶段检查点 + 状态回读 + 数据把关**。本文件说明 Skill 如何应对，所有方法均来自本机工作区已验证的实践。

## 1. 核心范式：阶段化拆解（已验证）

工作区现有复杂实验都采用编号阶段脚本，这是处理复杂性的成熟方式：

| 项目 | 阶段数 | 阶段示例 |
|---|---|---|
| brazil-pfc | 6 | 成样 → 预压 → 胶结 → 卸载 → 加载 → 导出 |
| hf-pfc | 8 | 水压致裂多阶段 |
| shpb-pfc | 4 | SHPB 冲击 |
| openpit-pfc | 11 | 露天开挖 |

**约定**（来自 `ARCHITECTURE.md`）：

- 阶段脚本：`<前缀>_<两位序号>_<动作>.py`，序号即执行顺序；
- 共享参数/几何：`<前缀>_geom.py`，由运行器拼接在各阶段之前；
- 无头入口：`*_console.py`；参数集中在 `data/`（GUI 与 console 共用），不写死在脚本里；
- 存档放 `work/`，成果放 `outputs/<模式>/`。

**为什么这样能支撑复杂实验**：每个阶段是一个可独立执行、可独立验证的单元；阶段之间是明确的检查点，正好对应 Skill 的"阶段级检查点"策略——不追求任意位置暂停，而是在阶段边界等待决策。

## 2. 六阶段协作循环（适用于任意复杂度）

```
阶段 N 开始
  → Agent 通过 itasca-mcp 提交阶段脚本（execute_task）
  → 运行中按需用 execute_code 在 cycle 间隙查状态（不中断任务）
  → 阶段结束，Agent 回读真实状态（check_task_status / execute_code）
  → 判断是否到决策节点：
      否 → 直接进入阶段 N+1（按已确认计划）
      是 → 按 reporting_policy 汇报：事实/趋势/解释/方案/待确认
          → 操作者决策（Chat 或 AUQ）
          → Agent 结构化决策，检查版本与风险
          → 必要时单独确认高风险操作
  → 阶段 N+1（参数版本 +1）
```

复杂度的增加只体现为**阶段数增多**和**决策节点增多**，不改变这个循环结构。

## 3. 长任务期间的三种状态访问

| 需求 | 工具 | 约束 |
|---|---|---|
| 提交可中断长任务 | `execute_task` | 返回真实 task_id；脚本在引擎工作区 |
| 运行中检查/调整 | `execute_code` | 与任务共享 `__main__`，cycle 间隙插入；同步调用有超时（默认10s，最大600s） |
| 查询进度与输出 | `check_task_status` | 分页 + filter + wait_seconds；SSE 事件用于内部等待，非实时推送 |

**关键**：GUI 用户操作需主动拉取 `POST /console_history`（0.6.17 实测；非独立推送，执行响应不含 `_context`）。想知道用户在 GUI 做了什么，必须显式调用该端点；Console 模式下该端点返回 `console_history_unavailable`（unsupported）。

## 4. 多实验并行与状态一致性

- 每个实验用 `experiment_id` 隔离；任务用真实 `engine_task_id` 关联；
- 文件变化 ≠ 模型已加载；命令输入 ≠ 执行成功；执行返回 ≠ 物理状态达到——必须回读 PFC 状态确认（三级证据：observed / executed / verified）；
- 用户中途改参数后，旧计划失效，必须重新验证模型状态；
- 高风险操作（覆盖/删除/重置/重算）单独请求授权，绑定具体动作与参数。

## 5. 数据质量把关（复杂实验尤其重要）

复杂实验阶段多、数据多，更容易出现"有数字但不可信"。执行 `reporting_policy.md` §5 的升级路径：

```
单点读数异常 → 多测点聚合 → 检查有效样本数 → 检查几何/边界
```

发现数据不可信时，**把"换测量方法/修正实验布置"作为决策项交给操作者**，不自行挑一个数字继续。回归案例：`E2E_DATA_QUALITY_AND_DECISION_RECOVERY`。

## 6. 维度差异（2D / 3D）

- 2D 坐标 `position=(x,y)`，3D 是 `vec3`；脚本不通用（已实测：2D 脚本入 3D 引擎报 "3D vector expected" 并 failed）；
- 3D domain 六参数 `model domain extent -3 3 -3 3 -3 3`；
- 接触模型命令两维度相同：`contact cmat default model linear ...`；
- 按 `engine` 选择正确脚本，不跨维度复用。

## 7. 已知限制（复杂实验的边界）

- 未验证跨实验类型通用性：当前 E2E 证据来自简化单轴压缩；三轴、颗粒流动等未验证；
- 3D 只做了 PoC 能力验证（T1–T8），未做完整协作 E2E；
- GUI 动态验证未做，特别是 GUI 用户上下文回传（G1–G6）；
- 任意位置暂停/恢复不支持，只有阶段级检查点；
- Agent 退出后后台主动通知不支持。

**结论**：复杂实验的处理方式是"**用阶段化把复杂性切开，用检查点把决策点固定，用状态回读保证真实性，用数据质量规则防止误判**"。这四点都在现有 Skill 规范内，不需要新增系统。超出已验证范围的实验类型，应先做小样验证再推广。
