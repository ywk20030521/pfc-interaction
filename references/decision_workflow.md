# 决策工作流：从用户回答到已验证的执行

## 1. 决策形成

用户的自然语言回答不是执行指令。Agent 必须：

1. 复述并结构化：明确参数值、动作、约束、执行条件；
2. 消除歧义：数值单位、作用对象、影响范围不清时先澄清；
3. 关联上下文：对应到 experiment / stage / task 与当前方案版本；
4. 形成 Decision：记录 decision、reason、approved_by、execution_status。

**区分**："接受实验方案" ≠ "授权所有后续操作"。覆盖文件、删除模型、重置等有重大影响的操作需要独立确认。

## 2. 风险分级

| 级别 | 示例 | 要求 |
|---|---|---|
| 低 | 查询状态、导出结果、继续监测 | 按计划执行，正常汇报 |
| 中 | 修改加载速率、调整记录频率、切换接触模型 | 复述确认参数与影响 |
| 高 | 覆盖/删除模型文件、重置模型、不可逆参数变更、长时重算 | 单独请求明确授权，绑定具体动作与参数 |

## 3. 执行前检查（Execution Gate 的逻辑，不实现为独立服务）

按顺序：

1. interaction 有效且未过期、未重复回答；
2. 实验/阶段/任务关联正确；
3. 方案版本未变化（变化则旧计划失效，需重新确认）；
4. 当前 PFC 进程、Bridge、任务状态健康；
5. 模型状态与提问时一致（用户修改后必须重新验证）；
6. 风险级别对应的授权已获得；
7. 高风险动作绑定到具体参数与文件。

任一项不满足 → 停止执行，进入澄清或人工处理，不盲目续跑。

## 4. 执行与验证

- 通过 itasca-mcp 执行已确定操作，不复制其工具；
- 执行后再次查询 PFC 状态或结果，确认操作真正生效；
- 执行失败保留失败状态与证据，不自动标记成功；
- 向操作者反馈：实际做了什么、验证结果如何、与预期是否一致。

## 5. 证据等级（不得混淆）

- `OBSERVED`：观察到输入、文件变化或事件；
- `EXECUTED`：有执行返回或任务记录证明命令已执行；
- `VERIFIED`：通过 PFC 状态/结果检查证明效果已生效；
- `INFERRED`：Agent 推断，不能作为高风险执行的唯一依据。

文件变化不代表模型已变化；命令输入不代表命令已执行；命令成功不代表目标物理状态已达到。

## 6. 恢复与过期处理

- 采用阶段级检查点，不承诺任意位置暂停/恢复 Python 调用栈；
- 用户介入后旧计划必须按最新状态重新验证；
- 迟到回答、重复回答、超过版本有效期的回答不得进入执行；
- 状态不确定时进入明确的安全等待或人工处理，不用 unknown 冒充成功。
