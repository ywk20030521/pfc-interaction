# pfc-interaction 运行时闸门性能报告

**日期：** 2026-11-27
**基准脚本：** `benchmarks/benchmark_runtime_gate.py`
**原始数据：** `benchmarks/results.json`
**命令：** `python benchmarks/benchmark_runtime_gate.py --rounds 5`
**环境：** Python 3.13.14 / Windows 11 (10.0.26300) / psutil 7.2.2
**范围：** 交互协议、停机协议、授权闸门与宿主能力探测；**未接入真实宿主 UI、AUQ 或 PFC**。

---

## 1. 方法

- 每个场景预热后执行 5 轮，记录单次调用延迟（`perf_counter`）；每轮使用独立对象，避免状态污染。
- 资源消耗：`time.process_time`、`psutil` RSS、`tracemalloc` 峰值分配（独立测量）。
- 稳定性：归一化输出签名（生成 ID 只保留存在性）、非预期异常计数、跨轮 RSS 增长。
- 生成 ID 不参与确定性比较，比较的是行为结果。

## 3. 稳定性

- **异常数**：全部 10 个场景 0 次非预期异常。
- **确定性**：全部场景归一化输出签名数量 = 1；授权生成路径的随机 ID 已按语义归一。
- **内存**：绝大多数场景 RSS 增长 0–8 KB；峰值 Python 分配 ≤ 14.4 KB（授权 + 版本变化路径）；未见跨轮单调增长。
- **长尾**：结构化提问与授权路径存在少量 0.25–0.35 ms 尖峰，与对象分配和 Python 调度有关，数量级仍远低于一次用户交互。

## 4. 结果分析

1. **运行时闸门开销可忽略。** 最重的“授权生成 + 执行闸门”均值 0.078 ms、P99 0.245 ms；相对一次真实用户确认（秒级）和一次 PFC 仿真（分钟级）完全不构成瓶颈。
2. **停机与投递路径是微秒级。** 参数缺失停机 0.018 ms、Native Chat 待答 0.024 ms、结构化投递 0.033 ms；这意味着“先提问、后执行”的安全约束几乎无性能代价。
3. **去重与版本失效有效且便宜。** 重复投递阻塞 0.027 ms、版本变化失效 0.073 ms；适合每次交互调用前执行。
4. **能力探测成本最低。** L0/L2 探测约 0.001 ms，可在每次会话启动时无条件执行，不再依赖历史宿主结论。
5. **重要边界。** 这些数字只证明 Python 协议层性能；宿主是否真的渲染卡片、Agent 是否真的停机等待、用户是否真的确认，均不由本基准证明。

## 5. 改进建议

| 优先级 | 建议 | 理由 |
|---|---|---|
| P1 | 在 Agent 会话启动时缓存一次 `probe_host_capability()` 结果，并在宿主切换时失效重探 | 成本已极低，但可避免误用上一宿主结论；语义价值大于性能价值 |
| P1 | 将 `HostInteractionAdapter` 去重键持久化到跨会话状态 | 当前只在实例内去重；跨会话重复打扰用户的风险仍存在 |
| P2 | 为 `ask()` / `gate_formal_execution()` 增加 CI 性能门槛（如 P95 < 1 ms）与确定性检查 | 防止后续协议扩展把停机路径变成重型路径 |
| P2 | 补充真实宿主 UI + AUQ 的端到端延迟与回写验收 | 本次仅覆盖协议层，不能声称端到端交互已通过 |
| P2 | 对长尾尖峰做一次 GC/分配剖析 | 当前尖峰仍在亚毫秒范围，仅在交互频率极高时才有意义 |

## 6. 结论

交互运行时闸门在全部关键路径上为**微秒到亚毫秒级**，稳定性与确定性良好；“先提问、后执行”的强制边界不具备性能阻碍。**端到端宿主交互仍未验证，本结果不得用于宣称卡片已显示或用户已确认。**
